# Background candidate eye-call, current versus v2, 2026-07-26

In-game side-by-side proofs for the owner's background eye-call. Generated by
`frontend/scripts/background_candidate_proof.mjs`, which is the only thing
permitted to write this directory (convention h.1).

**Nothing here is adopted.** The shipped `bg_base.jpg` is byte-unchanged by the
session that produced these; the candidate is served to the browser through
`App.svelte`'s DEV-gated `?bg=` parameter and is pruned from the built bundle.

## The three views, and why these numbers

The presets are the platform's own, transcribed from the Developer Testing
Tool's Screen menu in `reports/qa/dtt_live_session_2026-07-26.md`. The owner
eye-calls beside a real DTT session, so the frames are the sizes that tool
actually serves rather than sizes of our choosing.

| File | View | Arrangement |
|---|---|---|
| `desktop_1200x675__current_vs_v2.png` | DTT Desktop, 1200 x 675 | stacked, current above v2 |
| `mobile_portrait_375x667__current_vs_v2.png` | DTT Mobile M portrait, 375 x 667 | beside each other, current left |
| `popout_s_400x225__current_vs_v2.png` | DTT Popout S, 400 x 225 | stacked, current above v2 |

Landscape frames are stacked and the portrait frame is set beside its pair, so
each individual frame stays as large as possible on a phone screen. The single
captures that compose each sheet are kept alongside as
`<preset>__current.png` and `<preset>__v2.png`.

## What was verified rather than assumed

`proof_results.json` records, per capture, the background `src` the page
actually served, that the image decoded (`naturalWidth > 0`), that the HUD was
present, and that no dialog was open. A capture labelled V2 that had silently
fallen back to the shipped file would be worse than no capture, so the label is
checked against the DOM rather than trusted from the URL. All six captures
verified.

Both arms of every pair come from one dev server and one build, differing only
in the `?bg=` parameter. Two separate builds could differ in ways nobody
intended, and the eye-call would then be reading that difference instead of the
background.

## Reading the frames

How much background each view actually shows differs a great deal, and it is
worth knowing before judging:

- **Desktop** shows the most. The scene reads to the left of the reel frame and
  across the full upper band, so this is where the choice is most consequential.
- **Popout S** shows the scene at both margins of the stage. Legible, second
  most consequential.
- **Mobile portrait** shows almost none of it. The stage and the HUD occupy
  nearly the whole pane, leaving a thin strip above the title and the band
  behind the FEATURES bar. On a phone the background choice barely registers.

The measured tonal differences behind those frames are in
`reports/qa/background_candidate_ingest.json`: against the incumbent, v2 runs
+15.43 mean luma overall, +17.81 across the stage band and +14.72 under the
bottom HUD strip.
