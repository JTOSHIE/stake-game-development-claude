## PER REQUIREMENT NOTES

**REQ-179, submission is an upload for assessment against criteria Carrot can change.** The
upload half is real and documented twice over: `SUBMISSION_DOSSIER.md` section 5b is the
step-by-step portal sequence, and `docs/records/upload-kit/00_READ_ME_FIRST.md` PART 9i is the
same sequence written for the owner ("Drag in **everything** in `FS_UPLOAD_KIT_V10/`, not a
subset"). What produces the uploaded artefact is `scripts/kit_build.mjs`, which refuses a build
nobody could reproduce. That script has a `--self-test` per convention (p), so it is better
defended than most, but **it is not wired into CI**: I grepped `.github/workflows/checks.yml`
for `kit_build` and got zero hits, so breaking the upload artefact's reproducibility would make
nothing go red. The second half of the requirement, assessment against criteria Carrot sets and
can change, has no proof at all, and the project's own claim register says why:
`reports/qa/compliance_register/PROJECT_CLAIMS.md:28` row R7-13 reads "UNRESOLVED: the
authoritative submission criteria list has never been read, because it sits behind portal auth;
it must be captured on the owner's next login before submission can claim checklist coverage."
I record that as context rather than as proof: `PROJECT_CLAIMS.md` is neither of the two tracker
files the rubric counts.

**REQ-180, only written notice is acceptance.** What exists is a discipline of not
over-reading portal state, in three places I opened: the walkthrough's "\"Publish\" does not
mean publish", the dossier's note that the approvals endpoint 404s until Start Approval is
pressed, and 5b step 6's "Do not request review yet". Nothing in the repository misstates
acceptance, so this is not NOT_MET. But **the rule itself is written nowhere**, and nothing
would fail if a future session's report or dossier section described a passing gate set or a
published portal version as acceptance. That is the finding. I looked in the tracker, the
charter, the dossier, the owner checklist, `COMPLIANCE_WATCH.md` and the whole of `checks.yml`.

**REQ-181, object code within 3 days of acceptance and updates within 10.** The delivery
MECHANISM is strong: `kit_build.mjs` clones the remote, refuses when HEAD is not reachable on
the remote or when tracked files under `frontend/` differ from HEAD, and stamps the bundle, all
of which I read in its header and its refusal list. The **timing obligation is completely
untracked**: grep for "three (3) days", "within 3 days", "ten (10) days", "within 10 days" and
"object code" across every `*.md` outside the platform capture and the register returns nothing,
so no document names a clock, an owner or a DONE-when for either window. The obligation only
bites after acceptance, which has not happened, which is why I graded NO_PROOF rather than
NOT_MET; a session that lands a modification after acceptance has nothing telling it a 10-day
clock started.

**REQ-183, Game Documentation.** This is the finding I would rank highest in the slice, because
it is load-bearing for two other requirements. `terms.md:227` defines Game Documentation as the
integration, operation and ongoing-management documentation we hand over, and `terms.md:369`
and `terms.md:353` then warrant that the GAME CONFORMS TO IT (the register's R9-03 and R9-12).
**No artefact in this repository is designated as that document.** The dossier's own thirteen-row
submission inventory has no row for it, and grep for "Game Documentation" across `docs/`,
`reports/` and the root markdown finds only `terms.md` and register or shard rows quoting
`terms.md`. Documentation that would SERVE exists and I opened one of it,
`docs/RGS_CONTRACT_REFERENCE.md`, which is genuinely integration documentation and is
cross-checked against `rgsService.ts`. But it is our own on-file reference, not a designated
deliverable, and a conformance warranty whose referent is undefined cannot be tested in either
direction. Proof: NONE, and no gate compares documented behaviour against built behaviour.

**REQ-185, all testing on all applicable operating systems and browsers.** NOT_MET, and this is
the plainest gap in the slice. Both CI jobs are `runs-on: ubuntu-latest` (`checks.yml:106` and
`:563`). The browser job installs exactly one engine, "npx playwright install chromium
--with-deps", and its cache key comment confirms the intent is one chromium build pinned to one
driver. Every one of the eleven browser legs is a chromium script; 86 files under
`frontend/scripts/` reference `chromium` and none launches `firefox` or `webkit`. What device
coverage exists is chromium's own emulation of iPhone 14 and Pixel 7 contexts, which the
project itself already says is not a real device, at self-assessment item 56. So no macOS, no
Windows, no Safari, no Firefox, and no real hardware anywhere in the automated evidence.
Severity HIGH rather than STREAM: a player on Safari could certainly see something wrong, but I
observed no rendered defect, and claiming one would be exactly the inference this audit forbids.
I checked whether the gap is already recorded and it is not: item 56 is about older mobile
devices, and the only tracker hit on Safari is TR-066, which is a `touch-action` fix, not a
coverage row. This does not match any row in `reports/qa/stream_test/KNOWN_OPEN.md`.

**REQ-186, identity and verification documents.** UNKNOWN, deliberately. Whether the owner has
submitted identification documents to Carrot is a platform-side fact that the repository cannot
observe, and I will not convert silence into a NOT_MET. What I DID establish, and what is worth
a marshal's attention, is that the obligation is untracked: `OWNER_CHECKLIST.md` claims a
complete enumeration ("**five things are outstanding**, and everything else that was ever on
this list is DONE with its evidence path recorded below") and identification and verification
document submission is in neither the five nor the DONE table, while the requirement it hangs on
is the licence fee becoming payable at all. Grep for "identification and verification",
"verification documents" and "KYC" across the tree outside the platform capture and the register
returns nothing substantive. `WRS_MASTER_DOCUMENT.md` section 1 covers ASIC business name
registration and holds the ABN offline by policy, which is a different obligation.

**REQ-187, continuous real-time access to the development environment.** The access itself is
plausibly granted, since `OWNER_CHECKLIST.md:52-54` states flatly that "This repository is
public", and I opened that line. Two things I could not establish. First, **no repository URL is
recorded anywhere I looked**: grep for `github.com/` in `WRS_MASTER_DOCUMENT.md`, `README.md`
and `COMPLIANCE_WATCH.md` returns nothing, and the register's own R9-30 row notes the platform's
registration requires "A link to your GitHub repository", so the link that constitutes the grant
is not recorded on our side. Second, nothing defends the grant: no gate reads repository
visibility, and if the repository went private tomorrow every check would still pass. The
presentability half is defended by a different mechanism, `checks.yml` running on every push to
main plus protocol rule 10, and I have deliberately not counted that as proof of this
requirement because it guarantees a green build rather than an access grant.

**On REQ-182 and REQ-184, the two SATISFIED rows, and what they do not cover.** REQ-182's proof
is genuine: `npm run build` runs in the static gates job on every pull request and every push to
main, so source that stops building goes red, which is exactly the "buildable state as of that
date" the clause asks for. One caveat a reader should have: `SUBMISSION_DOSSIER.md:259-262`
records that the repository holds seven of the maths publish files and the five
`books_<mode>.jsonl.zst` are deliberately not committed, so a Source Code delivery taken from
this repository alone hands over the generators and the lookup tables but not the books. That is
a recorded and ruled decision, not a defect, and the books are regenerable, so I did not treat
it as breaking the row. REQ-184's proof is committed evidence rather than a gate: eighteen
frames from a real portal session on `future-spinner-2`, catalogued with what each frame shows
kept apart from what it proves, plus `OWNER_CHECKLIST.md:143`'s Cruise money row closing TR-075
to the cent. That is pre-launch functional testing staffed and funded by us, which is what the
clause asks. It is not a matrix, which is REQ-185's problem, and several DTT items remain open
by the walkthrough's own account (Gold Coins parked for want of a GC session, feature resume
unconfirmed against the live platform).
