## PER REQUIREMENT NOTES

### REQ-079 (no session, no authorisation)

Implementation is real and I read the whole of `ReplayMode.svelte` (508 lines) to confirm the
negative: its import block imports `replayService`, `utils/currency`, `replayStore`, five
components, `roundInterpreter`, `socialMode`, `gameStore` writables and the i18n helpers, and
`rgsService` is **not** among them. `App.svelte:1170`'s `if (isReplay) return` sits above every
line of RGS initialisation, and `App.svelte:1689-1691` renders `<ReplayMode />` instead of the
whole live tree. `fetchReplay` sends `{ method: 'GET' }` with no header object at all, so no
token can travel.

The proof is the problem. `frontend/scripts/replay_blocker_proof.mjs` is the only artefact that
loads the built game from a session-free URL and requires it to reach `START REPLAY`, and it is
**not wired into CI**: I read every `- name:` step in `.github/workflows/checks.yml` (69 of them,
static job plus the ten-entry browser matrix at lines 570-600) and no step runs it. Grading it
SCRIPT_UNWIRED rather than CI_GATE. It also has no self-test for THIS class (its convention (p)
seed is the z-index interception, not a session requirement), and the live frame
`01_replay_22975_...png` cannot serve as evidence here because it was captured inside the
platform's own logged-in developer panel, so it says nothing about the anonymous case. If someone
added an `authenticate()` call to `ReplayMode.onMount`, nothing in this repository would go red.

### REQ-080 (the six required parameters)

All six are read at `replayService.ts:59-71`, `replay` as the mode gate and the other five as
mandatory with a throw, and `App.svelte:37-44` deliberately still routes a malformed replay URL
into `ReplayMode` so the error card shows rather than falling through to the live game. Four of
them are then consumed in the request path at line 125.

No test in the repository calls `parseReplayParams`. I checked all 20 test files by name and
grepped the tree: the only references outside `App.svelte` and `ReplayMode.svelte` are two
comments (`utils/currency.ts:96`, `utils/currency.test.ts:51`) and one in the locked
`rgsService.ts:491`. Gate 13 tests the interpreter mapping, not the parse. So the six-parameter
contract rests on the unwired browser proof, plus partial visible corroboration in
`reports/screens/replay-blocker/02_base_ready_eur.png` (`Mode: BASE` proves `mode` was read).
`game`, `version`, `event` and `rgs_url` have no artefact that would fail if one were dropped,
because the harness's route glob matches any URL.

### REQ-081 (the five optional parameters)

Four of the five are genuinely applied, and I quoted each: `currency` (default `USD`, or `SC`
when social) drives `currencyCode.set` and `formatBalance`; `amount` is guarded against NaN and
non-positive junk and drives `betAmount.set`; `lang` selects the disclaimer, the button strings
and the number formatting; `social` is derived from the flag OR `isVirtualCurrency(currency)`,
which the file explains at 77-96 and which can only ever turn social ON.

**`device` is accepted and never applied.** It is typed on `ReplayParams` (line 31), defaulted
(line 115) and then read by nothing: `grep -rn "\.device" frontend/src` returns no hits, and the
only other occurrence of the word in the replay surface is a comment. Replay adapts to device by
CSS instead (`ReplayMode.svelte:491` `@media (max-width: 480px)`). I graded this SATISFIED rather
than NOT_MET because the governing platform text is a parameter table row, `device No Device
type`, which states no required behaviour; the slice's paraphrase "apply them where present" is
the stricter reading and under it `device` is dead. Recording it as LOW so the marshal can see it.

**A second asymmetry, recorded because it is unproven either way.** The live path validates the
launch language through `resolveLaunchLocale(raw, socialAtBoot, locales)` (`App.svelte:190-191`),
which `socialLocale.test.ts:67-71` exercises against `null`, `''`, `'xx'`, `'EN-GB'` and six other
junk values, all resolving to `'en'`. `ReplayMode.svelte:48,274` does **not** use it: it does
`const initialLang = (search.get('lang') ?? 'en') as Locale` and `locale = (params?.lang ??
initialLang) as Locale`, a bare cast. Whether `t()` degrades gracefully on an unshipped code is
something I did not establish, so I am not claiming a defect, only that replay's lang handling is
not the gated one.

### REQ-083 (the GET path shape)

The single line at `replayService.ts:125` builds exactly the documented shape, with `rgs_url`
scheme-prefixed at 73-75 if the platform sends it bare, and line 131 is a `GET`. That is correct
today and nothing defends it. Where I looked: all 20 test files (none imports `fetchReplay`),
every step in `checks.yml`, and the one browser harness, whose interception is
`await page.route('**/bet/replay/**', (route) => route.fulfill({` at line 82. A wildcard glob
matches `/bet/replay/1/BASE/{game}/{event}` just as happily as the correct order, so even if the
harness were wired it could not catch a transposition. Reordering two segments would ship a replay
that fails against the real RGS while every gate in the repository stayed green.

### REQ-084 (payoutMultiplier, costMultiplier, state)

All three fields are consumed, and the consumption is correct. The live capture is the strong
part: the platform panel sent `Amount 750`, `super`, event `22975`, and the game rendered
`MULTIPLIER 5000.0x` / `WIN 3750000.00`, which is 5000 x 750 exactly. So on the real endpoint
`payoutMultiplier` is a plain bet-multiple, matching the platform's own `"payoutMultiplier": 25.0`
example, and `ReplayMode`'s `payoutMultiplier * params.amount` and `>= WINCAP` (5000) are both
right.

**THE INSTRUMENT IS WRONG, AND ITS COMMITTED EVIDENCE IS WRONG BY 100x. New finding.**
`replay_blocker_proof.mjs:82-88` fulfils the replay response with `payoutMultiplier:
round.payoutMultiplier` taken straight from
`frontend/src/lib/services/__fixtures__/replay_rounds.json`, whose values are **centibets**, not
bet-multiples. I read the fixture: `base.win` is `390`, every `cap` is `500000`, and
`roundInterpreter.ts:40` labels the field `payoutMultiplier: number // centibets` with
`CENTIBET_CAP = 500_000 // 5,000.00x in centibets` at line 23; `replayRounds.test.ts:129-130`
confirms the unit by asserting `Math.round(summed * 100) === round.payoutMultiplier`. So the
harness feeds 390 where the RGS would send 3.90. The consequence is visible in the committed
frame I opened for REQ-087: `reports/screens/replay-blocker/04_base_complete_play_again.png`
shows `MULTIPLIER 390.0x` and `MEGA WIN!!! €3,900.00` on a €10.00 bet for a round that pays
**3.90x, that is €39.00**. The header comment at line 26 compounds it, describing the pass 3
round as "payoutMultiplier 5000" when the fixture it passes is 500000.

Two things follow, and both are proof-path findings rather than product findings. First, the
harness cannot detect a scale error in either direction: with 500000 fed in, the wincap branch
fires because 500000 >= 5000, so pass 3 would go green even if `ReplayMode` divided or multiplied
by 100. Second, `reports/screens/replay-blocker/` is cited as evidence in
`SUBMISSION_DOSSIER.md:640` and `reports/screens/EVIDENCE_INVENTORY.md:26`, so an external
reviewer opening frame 04 sees a Bet Replay win figure that is 100x the round's true payout.
Per convention (l.8) this is money-display adjacent and is written as a question, not a ruling:
the correct repair is to the fixture feed or the harness, not to the shipped code, which the live
frame vindicates.

`costMultiplier` is the one field with no proof at all. It reaches
`totalBetSpentMicros(params.amount, response.costMultiplier)` and is only rendered when
`response.costMultiplier !== 1.0` (`ReplayMode.svelte:271`), so the base-mode frames cannot show
it, and pass 3 (which passes `400.0`) clicks straight through the ready state without asserting
the cost line. Gate 13 covers the `state` third of this requirement and nothing else.

### REQ-085 (auto-load without interaction)

`onMount` parses and fetches with no gate, and `phase` moves `loading` to `ready` on its own; the
platform's companion sentence, "Display 'Play' button - Once loaded, show a play button", is what
`START REPLAY` is, so the button is required rather than a violation of auto-load. The assertion
that would fail if a click were introduced is `page.goto` followed directly by
`.start-replay` `waitFor({ state: 'visible' })` in the unwired harness. Committed frame 02 shows
the reached ready state but a still image cannot testify that no interaction occurred, so I graded
the harness rather than the frame. NO_PROOF stands on the wiring, not on the code.

### REQ-086 (identical presentation, not a summary)

This is the one requirement in the slice with a genuine CI-wired gate, and it is a good one: gate
13 runs on every push, drives five round categories per mode from **real book rounds** rather than
hand-written fixtures (its own header explains why at lines 15-19), asserts a full 5x4 board with
every cell named, and asserts the presented wins sum to the book's declared payout. Gate 13a then
reads the shipped component and asserts the deleted legacy search has not returned and that
`interpretEvents` is called exactly once, outside the `freeSpinTrigger` branch.

Two weaknesses worth recording. The test **restates** the component's mapping rather than
importing it, because a `.svelte` script block cannot be imported by tsx; the file admits this at
lines 21-25 and 13a is the mitigation, but a mapping change inside the component that the source
scan does not pattern-match would not be caught. And the gate has no convention (p) seeded
self-test: `checks.yml:420-422` runs the test once with no `--self-test` leg, unlike the nine
browser gates in the matrix, which all run `--self-test &&` first. The "THE REGRESSION" block at
lines 66-79 is the nearest thing to one, and it guards the books rather than the gate.

### REQ-087 (final results stay visible)

Satisfied and visibly evidenced. Beyond the quoted template guards, `playAgain()` at 256-264 is
the **only** thing that clears the win state and it needs a click, and the max-win reordering at
233-246 exists so a capped replay ends on its splash with nothing running underneath, which is the
owner's 2026-07-28 order applied to this surface.

Two observations from opening frame 04, neither of them new. The win pod overlaps the right end of
the `REPLAY AGAIN` button, which is a replay-surface pod placement issue and matches
**KNOWN(TR-114)**, "The replay ghost pod. Replay surfaces are outside the watched session". The
pod prints `MULTIPLIER 390.0x` with a letter `x` while other surfaces use the multiplication sign,
which is **KNOWN(Q-26)** and is explicitly recorded there as under-enumerated across components.
The amount itself is the 100x instrument defect written up under REQ-084.

Proof grading note: the browser leg that guards the max-win hold in CI,
`.github/workflows/checks.yml:589-590`, `- name: "browser: max-win hold"` /
`run: node scripts/max_win_hold_gate.mjs --self-test && node scripts/max_win_hold_gate.mjs`,
does **not** exercise replay. `grep -rln "isReplay\|replay=true\|bet/replay" frontend/scripts
scripts` returns exactly one file, `replay_blocker_proof.mjs`. So the owner-ordered hold
reordering inside `ReplayMode.startReplay` is defended by a live-play gate that never enters this
code path.

### The cross-cutting finding, stated once

Bet Replay is a **mandatory** approval requirement and a publicly shareable surface, and the
repository defends it with exactly **one** CI-wired gate covering one of these nine requirements'
substance (gate 13, the interpreter mapping, `checks.yml:420-422`). The seven-assertion browser
proof that covers session-free load, auto-load, the real click, the presentation running, EUR
formatting and the wincap flow exists, is well written, carries a genuine seeded-red pass, and is
**not in `checks.yml`**. Wiring it would close REQ-079, REQ-080 and REQ-085 at once; fixing its
fixture scale first is a precondition, or the wiring would enshrine the 100x figure.
