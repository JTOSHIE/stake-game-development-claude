## PER REQUIREMENT NOTES

### REQ-100 (exclusive RGS transport)

Platform text: "Session authentication and bet transactions are handled exclusively through
the Stake Engine RGS." Opened the locked `rgsService.ts` and confirmed authenticate, play
and end-round all address `${params.rgs_url}/wallet/...`. I then enumerated every network
caller in `frontend/src` (`fetch(`, `XMLHttpRequest`, `new WebSocket`, `sendBeacon`,
excluding test files): exactly three, listed in the table. There is no studio wallet, no
session service and no telemetry transport. `replayService.ts` uses the same `rgs_url` host
on the public `/bet/replay/` path, which CLAUDE.md's compliance section records as
deliberate ("Replay never calls rgsService or wallet endpoints, uses the public
`/bet/replay/` endpoint").

WHAT I COULD NOT ESTABLISH. The CI gate proves the three endpoints are addressed correctly;
NOTHING gates the "nowhere else" half. My enumeration of network callers is my own grep at
this HEAD, not an assertion anything re-runs. A telemetry `fetch` added to a component
tomorrow would go red nowhere. `frontend/scripts/dead_wiring_scan.mjs` is wired
(`checks.yml:195-196`) but scans dead state, not egress. I still graded this SATISFIED
because the proof path that exists is real and wired, but the absent egress gate is worth a
marshal cluster with REQ-104, which fails for the same missing instrument.

### REQ-101 (authenticate drives the ladder) — SATISFIED, with one half of the platform sentence NOT respected

Graded SATISFIED because the ladder half is implemented and gated, but the verbatim platform
text is wider than the slice's paraphrase and the wider reading is not fully met, so it is
recorded here for the marshal rather than buried.

Platform verbatim: "The authenticate HTTP response returns default bet levels, supported bet
levels for a specified currency, and minimum/maximum bet amounts. The frontend must respect
these values." THREE groups. Only ONE is published out of the locked service. I opened
`rgsService.ts` and grepped every consumer:

- `betLevels` — published: `rgsService.ts:735` `    rgsBetLevels.set(auth.betLevels)`. Respected.
- `defaultBetLevel` — parsed at `rgsService.ts:569` `    defaultBetLevel: microsToDisplay(config.defaultBetLevel ?? 0),` and then read by NOTHING. Grep over `frontend/src` for `defaultBetLevel` returns only the three declarations inside `rgsService.ts` (lines 171, 271, 569) and one comment at line 30. The game therefore starts on ITS OWN default bet and snaps it to the nearest authenticated level (`HudOverlay.svelte:142-144`), not on the platform's `defaultBetLevel`.
- `minBet` / `maxBet` — parsed at `rgsService.ts:565-566` and likewise read by nothing outside the file.

The snap DOES defend the specific failure the platform's own example names ("If the default
bet size is 1 unit but the session uses JPY (minimum bet size: 10 units), the play/ request
will fail"): after the snap the bet is always a member of `config.betLevels`, so a play
request cannot carry an unauthorised amount. That is why the verdict is not NOT_MET. What is
not respected is the platform's CHOICE of opening bet. Fixing it is a passthrough in a LOCKED
file (`frontend/src/lib/services/rgsService.ts`), so it needs an owner sanction; recording the
lock rather than proposing the edit, and noting it is the same one-line locked passthrough
REQ-102 needs for `stepBet`, so one sanction would close both.

### REQ-102 (minStep)

Platform text: "Bet increments must reflect allowed values within
authenticate/config/minStep." Graded NO_PROOF rather than SATISFIED, and the reason is a
distinction the repository itself makes in writing rather than one I inferred.

`betLadder.ts:105-112` argues minStep holds BY CONSTRUCTION: every offerable value came out
of `activeBetLevels`, which is the authenticate response's own `betLevels`, and nothing
rounds, interpolates or synthesises. I opened that and it is true of the code:
`setBetLevel()` refuses off-ladder values, `increaseBetLevel`/`decreaseBetLevel` index the
ladder, and every guard requires `idx > -1`.

But `minStep` itself is NEVER READ. `BetSelector.svelte:25-32` states this plainly and is
worth quoting because it is the repository confessing the gap: "A defensive assertion that
each level is itself a whole multiple of `config.stepBet` is NOT possible today and is not
faked: `stepBet` is read by `rgsService.authenticate()` into its `AuthResponse` and then
dropped, because only `betLevels` is published to a non-locked store. Adding the
passthrough is a one-line change to a LOCKED file and this brief carries no lock exception,
so it is parked with a named sanction request in the session report rather than routed
around." I confirmed this by grep: `stepBet` appears in `rgsService.ts` at lines 170, 267
and 567 (`stepBet: microsToDisplay(config.stepBet ?? 0)`) and NOWHERE else in
`frontend/src`. Note also that the platform capture names the field `minStep` while the
implementation reads `config.stepBet` from the pinned ts-client shape; the two names are
not reconciled anywhere I could open, and I could not establish which the live wire sends.

So the proof grade is deliberately hedged. `bet_selector_gate.mjs` IS wired at
`checks.yml:594-595` and it does carry a convention (p) seeded self-test that plants the
removal of the off-ladder refusal (`const seededLadder = ladderSrc.replace(/if \(!levels\.includes\(level\)\) return false/, 'if (false) return false')`)
and requires the gate to go red. That is real proof of the CONSTRUCTION argument. It is not
proof of the REQUIREMENT: if the RGS sends a `betLevels` array that is not itself a set of
whole `minStep` multiples, nothing in this repository notices, because the field it would
have to compare against is dropped inside a locked file. `rgsService.ts` is LOCKED
(`frontend/src/lib/services/rgsService.ts`), so the one-line passthrough needs an owner
sanction; recording the lock rather than proposing the edit. Not matched to any
`KNOWN_OPEN.md` row.

### REQ-103 (min and max selectable) — SATISFIED, with the gate's own assumption named

The panel lists every member of `activeBetLevels` and `bet_selector_gate.mjs` proves one tap
reaches both ends, in all four layout profiles, against an eight-level irregular ladder that
shares no value with the built-in one. `setBetLevel()` deliberately does NOT enforce
affordability (`betLadder.ts:113-119`: "Affordability is deliberately NOT enforced here"), so
the RGS maximum stays SELECTABLE even when the balance cannot cover it, which is what this
requirement asks for; the stepper arrow is the surface that caps at
`maxAffordableLevel`. Both are correct and are different acts.

THE ASSUMPTION I COULD NOT DISCHARGE. The requirement is "as dictated by the RGS", and the
RGS dictates min and max in TWO places: as the endpoints of `config.betLevels`, and as
`config.minBet` / `config.maxBet`. The game only ever sees the first, because minBet and
maxBet are dropped inside the locked service (see the REQ-101 note). The gate's fixture
assumes the two coincide by construction — `bet_selector_gate.mjs:110-111`
`    minBet: ODD_LADDER_MICROS[0],` / `    maxBet: ODD_LADDER_MICROS[ODD_LADDER_MICROS.length - 1],`
— so a session where `config.maxBet` exceeds the top authenticated level would be unreachable
in the UI and neither the code nor the gate would say so. I could not establish from anything
in this repository whether the live RGS can send such a session; the pinned ts-client shape
allows it. Recorded as a MEDIUM sub-finding rather than changing the verdict, because on the
data the game actually receives the requirement is met and is gated.

### REQ-104 (static only, no external sources)

Platform text: "The game build must consist only of static files and cannot reach external
sources." Implementation is genuinely clean: Orbitron is self-hosted through `@fontsource`
(`main.ts:2-4`), and the grep CLAUDE.md's compliance section prescribes
(`fonts.googleapis.com|fonts.gstatic.com`) returns empty, as does a wider grep for `cdn.`,
`unpkg` and `jsdelivr` over `frontend/src` and `frontend/index.html`.

THE PROOF IS THE FINDING. I opened `reports/qa/build-diet-network-log.json` and it is good
evidence of a past state: 52 requests, every one on `http://localhost:62276/`, zero
external, and its `summary` block reads `"notFound": 0, "failed": 0, "consoleErrors": 0`,
with the font served from our own origin (`/assets/orbitron-latin-...`). But per the audit's
own grading rule this is decoration, not proof: adding a Google Fonts link tomorrow would
not make that committed file visibly wrong, it would only make it stale. And the script that
produced it, `frontend/scripts/build_diet_verify.mjs`, is NOT a step in `checks.yml` (I read
the whole 671-line file and grepped it; `build_diet` appears only inside a comment at line
473, which is itself the record that this script "sat broken for ten days while its committed
result was cited as compliance evidence"). Even wired, its stated assertions are "zero 404s
and zero requests into any pruned legacy path", not zero external hosts.

So: no CI gate asserts the class the platform names, and the one named common failure
(external fonts) is defended only by a grep written into CLAUDE.md for a human to run. That
grep has no self-test and cannot go red. HIGH rather than STREAM because the failure is a
console error and a blocked request rather than a wrong pixel, though a font that fails to
load IS player-visible.

### REQ-108 (the currency display table)

Platform text: the table at capture lines 51 to 100, header "Currency Abbreviation Display
Example". This is the one requirement in my slice where I opened the implementation surface
and the requirement is NOT satisfied, so I derived the answer rather than asserting it.

`currency.ts` has two paths. When the session supplies `CurrencyDisplay` metadata
(`{symbol, symbolAfter, decimals}`), `formatBalance:185-195` honours it exactly and would
render the platform's token on the platform's side. That path is correct and is tested
(`currency.test.ts:116-124`). But the metadata is optional and the repository records that
it may never arrive: `rgsService.ts:582-584` labels `currencyDisplay` "UNKNOWN at the pin".
Absent it, fiat falls to `Intl.NumberFormat(localeTag, {currencyDisplay: 'narrowSymbol'})`
(`currency.ts:213-220`), which resolves the symbol and its SIDE from CLDR, not from the
platform table.

### REQ-105, REQ-106 (recorded briefly, both plain SATISFIED)

REQ-105: no baked endpoint exists. `parseSessionParams` throws when `rgs_url` is absent
rather than falling back, and `App.svelte:1195` gates live mode on the parameter being
present: `      (params.get('sessionID') !== null || params.get('session') !== null) && params.get('rgs_url') !== null,`.
The one nuance worth recording is that the parameter is a bare HOST, and the normalisation
that makes it a URL (`normaliseRgsUrl`) is itself a past defect's fix: `rgsService.ts:489-493`
records that the file "did not, so every wallet request went to a relative path on our own
origin and could not have reached the RGS at all". That is exactly the class this requirement
exists to prevent, it is fixed, and the fix is gated.

REQ-106: the gate's `required` list is derived from the `Translations` interface rather than
from `en`, which is the property that makes it able to fail ON `en`. Had it been derived from
`en`, English would have been complete by definition and the gate would have been decoration
for this requirement. It also asserts `if (locales.length !== 16)`. The gate carries seeded
self-test cases in-file (`locale_completeness_check.mjs:452,476` reference the TR-091 seeds),
which is convention (p) satisfied for the hardcoded-literal half; I did not verify that the
completeness half specifically ships a seeded missing key, and note it as a small unverified
corner rather than claiming it.
