at `vocabulary.ts:87-88`. What I could not establish: whether `hudSpinCost` or `costLabel` has a
social variant at all, since the platform's table does not restrict the bare word "cost" and I found
no override for either key. Not a finding, recorded so the next reader does not re-derive it.

**REQ-033 ("credit" to "balance").** The word occurs nowhere in the frontend source outside the table
row, and the balance readout is already overridden to the social wording at `translations.ts:1975`
(`balance: 'COINS',`). Note that the platform's replacement for "credit" is "balance" and this
product's social label for balance is "COINS", which is the platform's own replacement for "cash"
(`vocabulary.ts:54`) rather than for "credit"; both are platform-sanctioned words and neither is
restricted, so this is compliant, not a conflict. Recorded because it looks like one at a glance.

**REQ-034 ("buy bonus" to "get bonus").** The real-money label is literally the restricted phrase
(`translations.ts:226`, `buyBonus: 'BUY BONUS',`) and the social override replaces it
(`translations.ts:2006`, `buyBonus: 'GET FEATURE',`), with the same treatment on the heading at
`translations.ts:1973` (`buyFeaturesHeading: 'GET FEATURES',`) and the body at `translations.ts:2007`
(`buyBonusDesc: 'Guaranteed scatter play, 100× play',`). Two things to record honestly. First, the
substituted wording is "GET FEATURE", not the platform's literal "get bonus"; the prohibition is met
because the restricted phrase is not rendered, and the platform's own row at
`vocabulary.ts:72` (`{ phrase: 'bonus buy', replacement: 'bonus / feature' }`) sanctions "feature" as
a replacement noun, so I read this as compliant rather than as a deviation. It is nonetheless a
substitution the platform did not spell out, and worth an owner eye. Second, this is the requirement
in the slice with the WEAKEST defence: gate 6a skips `{...}` attribute values
(`a11y_social_terms_check.mjs:103`, `if (value.startsWith('{')) continue`) so it never sees a `$tr`
rendered label; `buyBonus` is not in gate 6b's `RULE_KEYS` or `GUIDE_KEYS`, and I grepped the test
files and found no assertion anywhere on `buyBonus`. If the `SOCIAL_OVERRIDES` entry were deleted,
"BUY BONUS" would render to a social player and **every CI gate would stay green**. The only thing
that would notice is the committed 2026-07-25 DOM harvest, which is a snapshot and does not re-run.
Cited as EVIDENCE, and flagged: this is a NO_PROOF-shaped gap wearing an EVIDENCE badge.

**REQ-035 ("withdraw" to "redeem").** The word occurs nowhere in the frontend source outside the
table row. There is no cashier surface in the game client, so absence is expected rather than
lucky. Gate 6a names the phrase and is the red-on-break for the a11y surface.

**REQ-036 ("be awarded to player's accounts" to "appear in player's accounts").** The row is
carried verbatim with the platform's curly apostrophe at `vocabulary.ts:73`, and `phraseRe`
(`vocabulary.ts:128-131`) was written specifically because `\b` does not bound `player’s`. No shipped
string contains the phrase; the closest are `prose.ts:193`
(`rulesWaysPay: 'Prizes are awarded left to right on adjacent reels starting from reel 1.'`) and a
doc comment at `ResumeOffer.svelte:28`, neither of which is the restricted phrase. **Two specific
weaknesses.** First, this is the one phrase in my slice that gate 6a does NOT list: I read the
whole `RESTRICTED` array at `a11y_social_terms_check.mjs:36-42` and it stops at 28 single- and
multi-word entries with no "be awarded" row, so the a11y surface is unguarded for it. Second, the
module's own doc comment at `vocabulary.ts:39-42` says the long phrases "are scanned for, not
rewritten, because a phrase like 'be awarded to player's accounts' needs an author, not a regular
expression" and that is **not what the code does**: `SUBSTITUTIONS` (`vocabulary.ts:95-105`) is
derived from all of `PROHIBITED_TERMS` and `sv()` skips only the three `NEVER_REWRITE` keys
(`vocabulary.ts:160`), so this phrase IS mechanically rewritten. Code and comment disagree; the
code's behaviour is the compliant one, so this is a documentation defect rather than a compliance
one. LOW, but recorded, because a reader trusting the comment would conclude a gap exists where
there is none, and a reader trusting the code would not know an author was meant to review this
wording.
