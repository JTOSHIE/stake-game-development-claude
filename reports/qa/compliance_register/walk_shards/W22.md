## PER REQUIREMENT NOTES

### REQ-048 (SATISFIED, MEDIUM, with two recorded weaknesses)

**A reading correction first, because the paraphrase and the platform text disagree and the platform
text governs.** The slice's paraphrase reads the sentence as three obligations: screen sizes, "no
lag", and "no low-quality audio". The upstream sentence is "Tested on a range of devices — renders
correctly across screen sizes with no laggy or low-quality sounds." Both adjectives attach to
"sounds": it is "no laggy ... sounds" and "no low-quality sounds", not a general frame-rate
requirement. So the requirement has two halves, screen sizes and audio, and there is no
render-performance obligation in this line. I graded it that way. If a marshal disagrees with the
grammar, the frame-rate half is ungated and would drop this to NO_PROOF, so the reading is
load-bearing and is stated rather than assumed.

**Screen sizes: closed by a wired gate.** The implementation is a single stage factor in
`App.svelte`, opened and quoted above. `layout_fit_gate.mjs` measures seven viewports its own
header says are "the platform's own, read off the DTT Screen menu", and the matrix leg
`browser: layout fit` runs it on every pull request and every push to main. Committed evidence sits
beside it at `reports/screens/layouts-2026-07-25/`, six PNGs named `desktop-1920x1080.png`,
`desktop-1280x720.png`, `landscape-compact.png`, `popout-400x225.png`, `portrait-390x844.png` and
`portrait-430x932.png`.

**Weakness 1, convention (p).** The `browser: layout fit` leg is one of only two in the eleven-leg
matrix that runs WITHOUT a `--self-test` prefix (the other is `browser: contrast`); the other nine
all run their seeded self-test first. I grepped `layout_fit_gate.mjs` for `self-test`, `selfTest`
and `SELF_TEST` and found nothing. So the gate carrying this requirement has never been seen to
fail, which is precisely the claim convention (p) exists to distrust.

**Sounds: green committed evidence, but reaching it requires care.** `reports/qa/audio_verify_2026-07-13.json`
is green on all eight checks including `"loopSeamsWithinTolerance": true`, with real measured seam
deltas (`"deltaDb": 0.037590003157419005` for `bgm_loop.webm`) rather than a bare boolean. A loop
seam within tolerance is exactly the "laggy sound" property: an audible gap or click at the loop
boundary is what that measurement rules out.

**Weakness 2, and it nearly caught me, so it is worth the marshal's attention.** The newest-NAMED
audio artefact, `reports/qa/audio_verify_2026-07-27.json`, records `"status": "PARTIAL - 5 of 8
pass"` with `"loopSeamsWithinTolerance": false` and six `"seamFailures"` of the form
`"bgm_loop.webm: decode failed: Unable to decode audio data"`. On a first read that looks like a red
audio result. It is not: line 100 of that same file explains the three reds were harness artefacts
proven by instrumenting `setOverdriveBed` under Fable ruling 23, because `runSeamChecks` "appended
the asset path AFTER the query string, so it decoded index.html instead of audio", and line 101
states `"do_not_cite": "This file records a harness fault. Do not cite it as evidence of an audio
defect."` **I had written the opposite into this shard before opening line 100.** The trap is
structural and should be recorded rather than left for the next reader: the file dated 07-27
declares itself superseded BY the file dated 07-13 (`"by": "reports/qa/audio_verify_2026-07-13.json"`,
`"on": "2026-07-25"`) while line 90 of the same file says it SUPERSEDES that same 07-13 file, and
both files carry timestamps in the 07-25 range (`2026-07-25T00:42:26.916Z` and
`2026-07-25T03:54:58.041Z`). The filenames, the `_meta.date` fields, the timestamps and the
supersession pointers are four sources that do not agree, and a reviewer who opens the
newest-looking one and stops reading concludes our audio fails. Cheap to fix by renaming or by an
index; expensive if a platform reviewer hits it.

**Third weakness: the audio proof is EVIDENCE, not a gate.** `audio_verify.mjs` appears nowhere in
`checks.yml` (`grep -c "audio_verify" .github/workflows/checks.yml` returns 0). So the sound half is
held by a captured artefact that nothing re-runs. If a future asset pass introduced a clicking loop,
nothing would go red and the committed JSON would keep saying `true`.

Cross-reference: not a KNOWN_OPEN row. The nearest entry is the note at KNOWN_OPEN.md lines 33-34
that "Cross-surface capitalisation and button casing (charter classes 4 and 7) are gated nowhere",
a different class. Reported as new.

### REQ-157 (NO_PROOF, MEDIUM)

Platform text: "Files/modes exceeding this size will fail on publish." The requirement is that the
check happens BEFORE upload.

**What exists.** `BOOKS_MANIFEST.md` is a real pre-upload measurement: it records exact byte counts
and row counts for all five books, measured 2026-07-28, with SHA-256 for each. Largest file is
151,905,143 bytes against a 4,200,000,000 byte cap, and 100,000 rows per mode against a 10,000,000
event cap. `SUBMISSION_DOSSIER.md:527` restates the outcome side: `| Outcomes per mode | max
10,000,000 | **100,000** per mode |`. Both margins are enormous, so I have no reason to think the
caps are breached.

**What does not exist is any check.** I looked in four places and quoted what I found in the table:
`checks.yml` has no size step; `validate_math.py` carries a `MIN_ROWS` floor and no ceiling and no
byte check, and is not in CI anyway; `kit_build.mjs` sums bytes without comparing them to anything;
`tools/verify_books_lookup_equality.py` is wired but only as `--self-test`, proving it fails closed
on absent books, which is a different property. So the caps are honoured by a one-off manual
measurement recorded in a markdown table, and if a future sanctioned maths pass raised the
simulation count, nothing mechanical would notice.

Two things I could not establish. First, whether the manifest's byte figures are re-derivable by
anyone without the private books: they are not in the repository by Fable ruling, so the manifest's
own hashes are the only handle, and I did not verify them (the files are absent by design).
Second, the platform's cap is on EVENTS per mode, not rows: `docs/records/reviews/sources/round2_review1.md:22`
records a reviewer making exactly that point, "The 10M event-count limit applies to events within
books, not round count; I cannot verify per-event counts". Our evidence counts rows. At 100,000
rows a mode would need 100 events per round to reach the cap, which is implausible for a 5x4 slot,
but that is my inference and not a measurement, and no committed artefact states the per-mode EVENT
count. Recording it as an open question rather than filling it.

One caveat on the figures themselves, stated because it is exactly the (l.4) trap. The self-audit's
column header is "Unique non-zero payouts", which is a count of DISTINCT payout values. The platform
sentence asks for "the number of non-zero weight payouts", which reads more naturally as rows whose
WEIGHT is non-zero. Those are different quantities. `docs/records/reviews/sources/round2_review3.md:42`
independently reports the weight reading, "Zero zero-weight rows across 500,000 lookup rows", and
line 173 of the same file repeats it. So both quantities are recorded somewhere in the repository,
but the evidence document that carries the platform's own sentence as its heading answers the
distinct-values reading, not the weight reading. **I could not establish which reading the platform
means**, and per (l.6) I am parking it rather than picking. It is a one-line addition to the
dossier either way.
