## PER REQUIREMENT NOTES

### REQ-001, functionality, clarity, communication, technical performance: UNKNOWN

Platform text: "Our team will inspect the game for functionality, clarity, communication, and
technical performance." There is no single implementation surface for this and I will not invent
one. What I opened: `.github/workflows/checks.yml`, whose second job runs ten browser legs
(`browser: layout fit`, `contrast`, `splash calm`, `turbo intensity`, `paytable card fill`,
`scrim coverage`, `win count-up steady`, `max-win hold`, `bet selector`, `preview server`, at
`checks.yml:571-600`), each of the last eight in the form
`node scripts/<gate>.mjs --self-test && node scripts/<gate>.mjs`, so they carry convention (p)
self-tests. Those defend fragments of "technical performance" and "clarity". They do not add up
to the requirement, and nothing in the repository decomposes these four axes into checkable
obligations, so I cannot name an implementation path or a proof path for the requirement as
written.

Bearing directly on the "clarity" axis, and recorded rather than re-discovered:
**KNOWN(C-01)** at `reports/qa/stream_test/KNOWN_OPEN.md:52`, "C-01's real cause is
`GameGrid.svelte:499`, `DROP_H = 520` ... The reel window is bare by construction for 312 of 412
pixels on every drop." I opened `reports/screens/stream-test-2026-07-28/006_desktop_base_idle.png`
and the idle grid does show twenty identical faint placeholder glyphs rather than the symbol set.
That is corroboration for an existing cluster, not a new row, and it is why this requirement is
UNKNOWN rather than SATISFIED: the axis a reviewer will judge is the axis with an open confirmed
cluster on it.

### REQ-002, no jackpot, gamble, continuation or early cashout: NO_PROOF

Implementation is real and I opened it. `frontend/src/lib/config/fsModes.ts:71-117` declares
exactly five modes (`base`, `cruise`, `antelite`, `bonus`, `super`) with costs 1.0, 1.0, 1.25,
100 and 400, and none is a gamble, double-up, collect or cashout mode. A repository-wide search
for the prohibited mechanics across `frontend/src` and `games/future_spinner/game_config.py`
returned exactly one hit, and it is the opposite of a violation:
`frontend/src/lib/i18n/vocabulary.ts:68`, `{ phrase: 'gamble', replacement: 'play' },` which is
the social-vocabulary substitution table. `COMPLIANCE_WATCH.md:13-15` records the project's own
claim, "No jackpot, gamble, continuation or early cashout", but a claim is not a check.

**The proof path is NONE, and that is the finding.** The nearest candidate is the CI-wired
`fsModes / index.json drift` step (`checks.yml:215-217`, `run: npx tsx
src/lib/config/fsModes.drift.test.ts`), and I opened the test to see what it actually asserts. It
compares the frontend mode table to the shipped maths index in both directions, including
`failures.push(\`index.json has a shipped "${shipped.name}" mode (cost ${shipped.cost}x) with no
matching fsModes.ts entry - the frontend cannot price or serve it\`)` at
`fsModes.drift.test.ts:42-45`. So a sixth mode appearing in the maths package would go red. That
is NOT this requirement. A gamble or double-up CONTROL added to the HUD, or a collect-and-continue
button, is not a bet mode, would not touch `index.json`, and nothing in the gate family asserts
the absence of that class of control. Severity HIGH because the class is a hard platform
rejection criterion with no machine guard at all.

### REQ-003, intellectual property: NO_PROOF (proof_kind EVIDENCE, partial)

Two halves, and they are in different states.

The NAME half is evidenced. `docs/records/trademark/2026-07-15/SEARCH_LOG.md:16-17` records
exact-phrase searches on IP Australia's official register returning 0 for both "we roll spinners"
and "Future Spinner", and the log quotes the register's own caveat rather than paraphrasing it:
"Word searching is very precise. An effective trade mark search should consider slight variations
of your trade mark, including plurals, common misspellings and trade marks that sound or look
very similar." The variant scan that caveat calls for exists as
`frontend/scripts/trademark_variant_scan_au.mjs`, which I read as text; its own header says "This
script only gathers data. It makes no clearance/similarity judgment", and it writes captures to
`docs/records/trademark/2026-07-18/au`, which exists alongside a `uspto` directory. I did not open
those captures.

The ASSET half has provenance for one asset and nothing for the rest.
`design-system/brand/GENERATION_NOTE_background.md` is a real provenance record for the
externally commissioned background: origin, supply date, source path, source SHA-256, source
bytes, shipped SHA-256, shipped bytes, and the vendor's own words. That is exactly the discipline
CLAUDE.md's assets rule requires, and it covers the highest-risk asset in the tree. It records
where the asset came from; it does not record an IP clearance or licence for it. For the rest of
the shipped asset set the only statement I found is a self-assertion,
`COMPLIANCE_WATCH.md:19-20`, "**Original IP:** verified. Original designs, produced in-house from
vector masters. No pre-purchased or third-party licensed content."

So: nothing goes red, and no committed artefact becomes wrong, if an asset without provenance
lands tomorrow. There is no gate that requires a generation record beside a new external asset,
which is the one mechanical check this class would actually support.

### REQ-004, no Stake branding or themes: NO_PROOF (proof_kind EVIDENCE, partial)

The implementation is better than a bare absence and worth quoting for its own sake. The platform
template disclaimer ends `TM and © 2026 Stake Engine.`
(`docs/stake-engine-live/2026-07-29/approval_guidelines_general_disclaimer.md`, the General
Disclaimer block). The shipped string does not copy it: `PaytableModal.svelte:62-64` appends the
studio's own notice instead, and the comment above it at lines 56-61 says why the sentence is not
translated, "it names the marks as registered and the copyright line is a legal notice". I
confirmed the rendered result in `reports/screens/rules-paytable-2026-07-25/09-disclaimer.png`.

A repository-wide search for `Stake` in `frontend/src` returns ten hits and every one is a source
COMMENT or a test comment naming the platform (`main.ts:1`, `App.svelte:181`, `:984`, `:1593`,
`socialMode.ts:4`, `:17-19`, `launchParams.test.ts:4`, `socialLocale.test.ts:3`). No player-visible
string carries the mark.

**The gap:** I found no gate asserting this class. I read `frontend/scripts/dist_hygiene_gate.mjs`
and `frontend/scripts/machine_tell_gate.mjs` looking for a Stake-mark assertion and neither
contains the string at all. The risk is concrete rather than theoretical: the platform's own
documentation hands an editor a paste-ready disclaimer that ENDS in a Stake trademark, and the
project has already had to consciously not paste it. A future locale pass that took the template
literally would ship a Stake mark into sixteen locales with nothing going red. I did not
enumerate audio, and I opened two frames out of the committed capture set, so the art and audio
halves of "anywhere" are unverified by me.

### REQ-005, subjective reviewer bar for taste and quality: UNKNOWN

The requirement is explicitly subjective ("Approval is at the discretion of the reviewer"), so
there is no threshold to test against and I will not record a verdict on a reviewer's judgement.
What is real and gated is a defined SUBSET. `docs/QUALITY_CHARTER.md:70` states bar B5, and
sections 96 to 102 map named machine-tell classes onto gate classes:
`mixed-apostrophe`, `double-space`, `orphan-placeholder`, `glyph-iconography`. The gate is
CI-wired with a seeded self-test (`checks.yml:285-291`), which satisfies convention (p) for the
classes it covers, and `QUALITY_CHARTER.md:411` states the wiring in the same terms:
"`frontend/scripts/machine_tell_gate.mjs`, wired into the `static gates` CI job."

Why UNKNOWN and not SATISFIED: the charter itself scopes the gate to "the sweepable subset", and
the surfaces this requirement is actually judged on carry open rows. **KNOWN(Q-27)**
(`KNOWN_OPEN.md:21`) records Vite scaffold CSS remnants including a stock Chrome focus ring
`rgb(0, 95, 204)` sitting on the last-touched control "through spin, win and COLLECT on a cyan and
magenta game", and `#app { text-align: center }` centring a legal paragraph.
**KNOWN(C-01)** is open on the reel window. Both are precisely the kind of finish a reviewer's
discretion lands on. The honest statement is that the mechanical subset is defended and the
subjective whole is open.

### REQ-006, no child or child-like characters, no appeal to minors: NO_PROOF (proof_kind EVIDENCE)

`design-system/DESIGN_SYSTEM.md:57-58` names the single identity character, "the racer plus hover
car". I opened `reports/screens/stream-test-2026-07-28/006_desktop_base_idle.png` and the figure

beside the car; there is no child, no child-like proportion, and no toy or juvenile motif in the

only the studio wheel emblem. `COMPLIANCE_WATCH.md:22` asserts "**No underage appeal:** verified.
No child or child-like characters", which is a claim rather than a check.

Why NO_PROOF rather than SATISFIED: I verified two frames out of a capture set of several hundred,
across one theme; the symbol set, the celebration overlays and the audio are unverified by me; and
the second half of the platform text ("promote, encourage, or are likely to appeal to underage
persons") is a tone judgement that shares REQ-005's subjectivity. Most importantly, a static PNG
cannot defend a prohibition: if a child-like character were added tomorrow, no gate, test or
committed artefact would change. Severity MEDIUM rather than HIGH only because the current state
is, as far as I looked, correct.

### REQ-009, same message as the template disclaimer: SATISFIED

I compared the shipped string to the platform template clause by clause, since the platform text
permits different wording but not different meaning. Template
(`approval_guidelines_general_disclaimer.md`, General Disclaimer block) against
`prose.ts:118`:

1. "Malfunction voids all wins and plays." -> identical.
2. "A consistent internet connection is required." -> "A stable internet connection is required
   to play."
3. "In the event of a disconnection, reload the game to finish any uncompleted rounds." -> "If
   your connection drops during a round, reload the game to finish any uncompleted round."
4. "The expected return is calculated over many plays." -> "The theoretical return to player is
   calculated over many thousands of plays and does not guarantee any result in a single session."
5. "The game display is not representative of any physical device and is for illustrative purposes
   only." -> "This game display is for illustrative purposes only and does not represent a
   physical device."
6. "Winnings are settled according to the amount received from the Remote Game Server and not from
   events within the web browser." -> "Winnings are settled according to the result returned by the
   Remote Game Server, not from events shown in the web browser." This also carries the template
   paragraph's own reason, "payouts are dictated purely by the RGS response and are not influenced
   by events on the frontend".
7. "TM and © 2026 Stake Engine." -> deliberately NOT reproduced; replaced by the studio's own
   notice at `PaytableModal.svelte:63-64`. Reproducing it would breach REQ-004.

All six substantive clauses are conveyed. The string exists in all sixteen locales:
`prose.ts:118` for English and fifteen `disclaimerBody` entries in
`frontend/src/lib/i18n/prose.locales.ts` (ar 71, de 147, es 223, fi 299, fr 375, hi 451, id 527,
ja 603, ko 679, pl 755, pt 831, ru 907, tr 983, vi 1059, zh 1135), and the type at
`prose.locales.ts:33` is a full `Record<Exclude<Locale, 'en'>, ProseStrings>`, so a locale missing
the key fails `npm run check`, which is CI-wired at `checks.yml:432-434`. That is the proof path
cited, and it is honest about its scope: it defends PRESENCE in every locale, not MEANING.

proof_notes, and this one is a real gate blind spot I established rather than assumed. The wired
`locale completeness` step (`checks.yml:223-225`) runs
`frontend/scripts/locale_completeness_check.mjs`, and that script reads
`const SRC = readFileSync(join(ROOT, 'src/lib/i18n/translations.ts'), 'utf-8')` at line 24. It
does not read `prose.ts` or `prose.locales.ts` at all, so the file the disclaimer actually lives in
is outside the locale gate's field of view; the type system is what covers it. And nothing anywhere
asserts the six clauses. An edit that dropped clause 4 or clause 6 from one locale, or from all
sixteen, would pass every gate in `checks.yml`. Related and already recorded, so not a new row:
`reports/qa/stream_test/shards/STV.md:22-23` documents the same malfunction clause existing in
four wordings across `prose.ts:114`, `:118`, `:197` and `:211`, which is the visible symptom of
this same absence of a content assertion.
