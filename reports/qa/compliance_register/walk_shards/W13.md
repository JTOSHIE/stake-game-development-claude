## PER REQUIREMENT NOTES

**REQ-142.** Platform text is "knowingly include in the Game any material that could
adversely affect Carrot or any of its Affiliate's name, image or reputation." I looked for a
mechanism, not a claim. `.github/workflows/checks.yml` was read end to end: every wired step
is enumerable and none of them reads on branding, offensiveness or asset tone. I grepped
`frontend/scripts/` and `scripts/` for `stake branding` and `trademark` and found only
`trademark_variant_scan_au.mjs`, which drives `search.ipaustralia.gov.au` for OUR OWN name
variants (`trademark_variant_scan_au.mjs:50`) and is a one-off research tool writing to
`docs/records/trademark/2026-07-18/au`, not a gate and not in CI. So the implementation path
I can honestly cite is a recorded POSTURE in `COMPLIANCE_WATCH.md`, and `REGISTER.md:18-22`
is explicit that project claims "must never be counted as requirements: doing so would let
the project's own assertion that it complies become evidence that it complies". The same
caution applies to using one as a proof path, so I have not. The finding is the absence of
any instrument: if an off-brand or reputationally awkward asset or string landed tomorrow,
nothing in this repository would go red. Under the register's own gloss of this clause
(off-brand assets), there is already an open instance, `docs/QUALITY_CHARTER.md:199` Q-27's
stock indigo in a cyan and magenta game, which I confirmed present at
`frontend/src/app.css:157-158`.

**REQ-143.** Nothing in the tree establishes third-party licence compliance. I opened
`frontend/package.json` in full: three runtime dependencies and eight devDependencies, one
of which resolves from a GitHub ref (`stake-engine": "github:StakeEngine/ts-client"`). I
opened the root `LICENSE` and it is "MIT License / Copyright (c) 2025 Stake Engine", i.e.
the upstream `math-sdk` licence, which covers the fork rather than the dependency set. What
I could NOT establish, and am recording as unestablished rather than assuming: whether the
tree is actually copyleft-free. I did not enumerate `node_modules` licence files, no
inventory exists to check one against, and asserting "these are all permissive" from
package names would be exactly the inference this audit forbids. So the honest position is
two-layered: the artefact the warranty requires does not exist (that is the finding), and
the underlying fact is UNKNOWN. An external reviewer already reached the same place at
`docs/records/reviews/sources/round2_review3.md:23`. Cheapest closure is a generated licence
inventory over the resolved lockfile, committed, plus a CI step that fails on any
GPL/AGPL/LGPL/SSPL SPDX id.

(`bet-modes-section.png`, `symbol-payouts-section.png`, `feature-access-section.png`,

**REQ-145.** Read as written: the Game's software must facilitate, i.e. must not obstruct,
the operator's source-of-funds and identity processes. The implementation is that the game
keeps no wallet and no identity of its own. Every money movement is a POST to the platform's
own RGS host carrying the platform's `sessionID`:
`rgsService.ts:552-553` (`/wallet/authenticate`), `:628-629` (`/wallet/play`, "sends
sessionID, mode and a NUMERIC micros amount" per the contract test at `:172`), and
`:666` where the header records "The official request body is `{sessionID}` ALONE".
`rgsService.ts` is a LOCKED path (`CLAUDE.md` locked files); I read it as text only and
propose no edit. The proof is `checks.yml:385-387`, which imports the real functions rather
than restating them. **State the inferential step plainly:** no assertion anywhere in this
repository mentions source of funds, KYC or identity verification, and none could, because
the game performs none of those processes. What the gate actually proves is that session and
wallet handling remains the platform's, in the platform's own shapes, which is what the
obligation reduces to for a game that never holds funds. If a future change introduced a
studio-side balance or a locally minted session, the contract test's URL and body assertions
would go red. Recorded weakness: like the drift test, this gate carries no seeded self-test
step in CI.
