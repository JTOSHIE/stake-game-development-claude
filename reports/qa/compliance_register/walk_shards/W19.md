## PER REQUIREMENT NOTES

### REQ-111 (SATISFIED)

Opened the boot path in `App.svelte` (`onMount`, lines 1168 to 1212) and the whole
session-state section of `rgsService.ts` (lines 505 to 813). The ordering is structural
rather than asserted: `_rgsMode` is set true only on the line after `await
authenticate(...)` resolves (`rgsService.ts:730,740`), and `spin()` routes to
`_mockSpin` while it is false, so `play` and `end-round` cannot physically precede a
returned authenticate. `evaluateLiveGuard(...)` at `App.svelte:1194-1198` then blocks
betting outright when authenticate errored, and the recovery call at 1205 is fenced
behind `if (!get(bettingDisabled))`.

Two things I could not establish and am recording rather than smoothing over.
First, **`/wallet/balance` is never called at all**: a grep for `wallet/balance` over
`frontend/src` returns nothing. The requirement is about not calling it before
authenticate, which is trivially met by never calling it, but a reviewer expecting a
balance poll will not find one. Second, **no test asserts the negative**: there is no
case anywhere that drives `play()` with `_rgsMode` false and asserts no fetch occurred.
The two CI gates I cite prove the launch is recognised and that recovery asks
`parseSessionParams` then `authenticate` in that order; neither would go red if someone
hoisted a `play` above `authenticate` inside `initRGS`.

### REQ-112 (NOT_MET) - the timing half of the basic flow

The platform text is explicit about ordering: "This flow takes creates a round and will
close the round after all animations have been complete. It accomplishes this by calling
the /wallet/play API and then calling the /wallet/end-round API when the round is
complete."

What ships closes the round **before** any animation. `endRound` is awaited inside
`_rgsSpinReal` (`rgsService.ts:800-803`), which is inside `spin()`, which `App.svelte`
awaits at line 1414 and only then calls `await gridRef.animateSpin(result.board)` at
1445. The free-spins presentation and the deferred `settleRound()` (1494) run later
still. So on a triggered round the platform believes the round is finished while the
player is still watching it.

The closure obligation itself IS met and IS gated: the wallet contract test asserts the
POST to `/wallet/end-round` with the official body, and `rgsService.ts:799` deliberately
gates on the platform's own `active` flag rather than our old `winMicros > 0` rule, with
the reasoning written out at 790-798. What is ungated, and what I am reporting, is the
sequencing.

**Why this is not cosmetic:** it removes the precondition for REQ-113. Session recovery
only fires when `round.active === true` on authenticate
(`sessionRecovery.ts:207`), and our flow settles every round before the presentation
begins, so a player who reloads mid animation or mid free-spins finds no active round to
resume. The recovery machinery is real, tested and CI-gated, and the flow it defends
against is one our own end-round timing largely forecloses. I did not find any comment,
tracker row or charter entry acknowledging this coupling; I looked in
`docs/records/reviews/REVIEW_TRACKER.md` (greps for the recovery rows), `CLAUDE.md`, and
the header comments of both `rgsService.ts` and `sessionRecovery.ts`. This is not a
match for any row in `KNOWN_OPEN.md`.

Note that `rgsService.ts` is a LOCKED path (`CLAUDE.md`, "Locked files"), so any change
here needs an owner sanction and the `LOCK-SANCTION:` token; the caller-side alternative
(deferring the close into `App.svelte`) would need the locked file to stop calling
`endRound` itself, so there is no non-locked fix.

### REQ-113 (SATISFIED, with one stated partial)

The verbatim platform text at `rgs_wallet.md:26` is "The round returned may represent a
currently active or the last completed round. Frontends should continue the round if it
remains active." That is met and well gated: `sessionRecovery.ts` inspects `auth.round`,
returns `none` unless `active === true`, interprets `round.state`'s events through the
canonical interpreter, presents before settling, and the CI-wired test asserts the
recorded call sequence puts PRESENT before endRound.

**The partial, stated plainly rather than buried:** `rgs.md:41` names the resume
position, "you can use the value found in round.event in the /wallet/authenticate API
response to know where to display the animations for that round from." **`round.event`
is never read.** The `OfficialRound` interface in the locked service declares it,
`rgsService.ts:182-191`:

```
export interface OfficialRound {
  betID:             number
  ...
  active:            boolean
  mode:              string
  event?:            string
  state:             unknown  // the round's game payload; see _extractRoundEvents
}
```

and `sessionRecovery.ts:96-101` then narrows its own `ActiveRound` to the three fields it
actually uses, "The official round, narrowed to the three fields recovery reads":
`betID`, `active`, `state`. A grep of all of `frontend/src` for `.event` (excluding
`.events`) returns exactly one hit and it is unrelated, `replayService.ts:125`'s replay
URL segment. So the field is typed, carried and dropped. The resume cursor comes instead
from a locally stored checkpoint, `validateCheckpoint(readCheckpoint(), script,
round.betID)` at line 235. The platform's wording is permissive ("you can use"), which
is why I have not marked this NOT_MET, but a local cursor and a server-side cursor are
not equivalent: a reload on a different device, a cleared storage, or a private-window
relaunch loses the position, where `round.event` would not. Worth a cluster row beside
REQ-112, since both are about the same flow.

### REQ-114 (NOT_MET) - the `device` parameter is parsed and dropped

Three of the four launch parameters drive real behaviour and are gated. `sessionID` and
`rgs_url` drive every request and are covered by the launch params gate and the wallet
contract gate. `lang` reaches the `locale` store before first render, at
`App.svelte:188-195`, with the gap it closed written out in the comment above it at
167-172: "rgsService.parseSessionParams() already read `lang` into SessionParams ... but
nothing ever published it to the `locale` store".

**`device` is the same defect one step earlier, and it is still open.** It is parsed at
`rgsService.ts:521-523` and stored on `SessionParams`, and I could find no reader. The
grep I ran was `grep -rn "'device'\|\.device\|device:"` over all of `frontend/src`, and
the complete result set is the type declaration (`rgsService.ts:253`), the parse
(`521-523`), and `replayService.ts:31,50,115` which parses its own independent copy and
also never reads it. So the platform's own statement of which device the player is on
reaches the bundle and changes nothing.

What I could NOT establish: whether the display is nonetheless device-correct by another
route. I did not audit the CSS for viewport media queries, which is the obvious
alternative mechanism and would make this a hygiene finding rather than a display defect.
That check is a separate surface and I ran out of budget for it rather than guessing;
treat the severity as MEDIUM pending it. No `KNOWN_OPEN.md` row covers `device`.

### REQ-115 (SATISFIED)

All three endpoints the game actually calls put `sessionID` in the body, and the wallet
contract test asserts the exact body of each against a recording fetch stub, so an
omission is caught per endpoint rather than in aggregate. The end-round case is the
strongest of the three because it asserts the body is `{ sessionID }` and nothing else.

One weakness worth recording: the gate is an ENUMERATION of three endpoints, not a rule.
A fourth wallet call added tomorrow without `sessionID` would pass CI green, because
nothing walks the module for `_post` call sites. This is the same instrument failure
`KNOWN_OPEN.md` records twice under "A parked list that enumerated its own class
incompletely". Also, per convention (p), `rgsService.contract.test.ts` is a test rather
than a gate script and ships no seeded-violation self-test; its assertions are concrete
enough that I am satisfied they would go red, but that is my reading of the source, not
an observed red run.

### REQ-116 (SATISFIED)

The runtime derivation is unambiguous and gated: the base URL comes only from the query
parameter, absence throws, and the bare host is given a scheme exactly as the official
client does. The comment at `rgsService.ts:489-496` records that this file previously did
NOT prefix the host, so "every wallet request went to a relative path on our own origin
and could not have reached the RGS at all", which is why the normalisation assertions
exist.

The half I could only partly close is "no build-time or constant RGS host anywhere in
the shipped bundle". I grepped `frontend/src` for `stake-engine` and every hit is a doc
comment or a `docs/stake-engine-live/` citation path, so there is no host constant in
source. **There is no gate that scans `dist` for a hardcoded RGS host.** I looked
through the `static gates` job in `checks.yml` (lines 105 to 515) and the dist-facing
steps are the dash gate, the machine tell gate, the asset reference gate and the dist
hygiene gate; none of them looks for a host. So the source is clean today and nothing
would tell us if it stopped being clean. I graded this SATISFIED because the
implementation requirement (take it from the parameter at runtime) is met and gated, but
the "nowhere in the bundle" clause is guarded by nothing.

### REQ-117 (SATISFIED)

`resolveLaunchLocale` lowercases and trims the raw parameter and validates it against the
shipped `locales` map rather than a hardcoded list, so the check cannot drift from what
ships, and all sixteen shipped keys are two-letter ISO 639-1 codes. The CI-wired test
iterates every shipped code and asserts it resolves to itself, and separately asserts
uppercase and whitespace normalisation, so a regional tag or a shouty `?lang=DE` is
handled.

The platform's list at `rgs.md:57` onward is seventeen entries, the sixteen we ship plus
"'da' (Danish)". We do not ship `da`, and `resolveLaunchLocale` returns `en` for it.
This is a known and recorded position rather than a fresh finding:
`docs/records/reviews/REVIEW_TRACKER.md:199` (TR-059) states "**`da` (Danish) is offered
by the platform and is not one of ours**, and the tail of the list is unread, so the true
coverage gap is not yet known", and it is PARKED by ruling; `REVIEW_TRACKER.md:256`
(TR-082) records the fallback observed live: "The game rendered clean English throughout
with no blank labels, no missing strings and no raw locale codes on screen." So the
tracker holds both the gap and its verification. Recorded here as a TRACKER_ROW
corroboration rather than a new row.

### REQ-118 (SATISFIED)

The drift gate is also the one gate in my slice whose failure MESSAGES I read rather than

### REQ-119 (NO_PROOF)

The implementation is right as far as I could read it. `roundInterpreter.ts` is the
canonical round reader and contains no currency reference at all; `betLadder.ts` mentions
currency only in a comment about ladder shape; `formatBalance` and `formatBalanceCompact`
are the only currency-aware functions and both take micros and produce a string. The one
place currency touches non-formatting logic is `socialMode.ts:87-93`, where `isSocial`
derives from `currencyCode` among others, and I opened it to check: it drives vocabulary
and the forced-English locale, both display, and the comment at 79-86 explains the three
signals as defence in depth. So currency does not reach round logic, bet arithmetic or
outcome selection.

**What is missing is any proof path.** Nothing would go red if a future edit made an
outcome or a bet step depend on the currency code. I looked at: `currency.test.ts` (CI
wired, formatting assertions only), `scan_wallet_floats.mjs` (CI wired, float-rounding
heuristic, and its own header calls itself "a line-level heuristic, not a type-aware
static analyser"), `currency_scale_drift.test.mjs` (CI wired, one constant),
`roundInterpreter.test.ts` and `roundInterpreter.determinism.test.ts` (NEITHER is wired
into `checks.yml`; a grep for `roundInterpreter` in that file returns no hits), and the
`static gates` job end to end. The determinism test is the natural home for such an
assertion and does not currently make one: it varies nothing but repetition, asserting
"same book in, byte-identical presentation out". Reporting this as the finding the brief
asks for: correct code with nothing defending it.

A related observation, recorded because it is cheap and someone should know: **two of the
twenty test files, `roundInterpreter.test.ts` and `roundInterpreter.determinism.test.ts`,

nothing back, against eighteen other test files that do appear as named steps. That is
outside my slice's requirements but it is the kind of gap the audit exists to catch.
