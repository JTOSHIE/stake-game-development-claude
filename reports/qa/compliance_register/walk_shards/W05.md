## PER REQUIREMENT NOTES

### REQ-088 (SATISFIED, with a proof weakness worth recording)

The Hide/Remove half is structural rather than conditional: `App.svelte:1689-1691` renders
`<ReplayMode />` INSTEAD of the entire live tree, so balance, bet selector, autoplay and the
theme selector are not present to hide. The Keep/Show half is all four items: win amount
(`WinDisplay`/`WinPod` at lines 307-312), replay controls (315-335), replay bet amount
(318-326), currency display (345-350), the last with its own comment quoting the platform
table. Frame 02 confirms all four render and none of the four Hide items do.

The weakness: the proof is a one-time capture. If someone re-added a balance readout to
`ReplayMode.svelte` tomorrow, nothing in CI would go red and the committed PNG would not
change. The script that made the capture, `replay_blocker_proof.mjs`, carries a genuine
convention (p) seeded pass (lines 104-125, the seeded interception that must go red, with
`fail('seeded interception goes red', 'seeded defect did NOT block the click; the proof cannot
see the defect it exists to catch')` as the negative control) but is
in NEITHER CI job, so this class is defended by evidence alone.

### REQ-089 (SATISFIED)

Two independent detection sites and they agree: `replayService.ts:59` is the strict
`!== 'true'` test, and `App.svelte:39-45` wraps it so that a malformed replay URL still
enters replay mode and shows the error state rather than silently falling through to live
play. That fallback is worth noting under the platform text "Detect replay mode", because it
means detection keys on the flag alone and never on the completeness of the other params.
Proof is EVIDENCE only; there is no unit test on `parseReplayParams` anywhere among the 20
test files (checked `launchParams.test.ts`, `currency.test.ts`, `vocabulary.test.ts`,
`replayRounds.test.ts`; `currency.test.ts:51` mentions the function in a comment about its
currency DEFAULT and does not import it).

### REQ-090 (NO_PROOF, HIGH)

The implementation is exactly what the platform asks: every one of the five path segments is
read from the query string, `rgs_url` is only normalised with a scheme prefix
(`replayService.ts:73-75`), and there is no default for any of `game`, `version`, `mode`,
`event`, `rgs_url` (they throw instead, lines 67-71). So the code is right.

What is missing is anything that would catch it going wrong. The only replay step in
`checks.yml` is gate 13, `npx tsx src/lib/services/replayRounds.test.ts`, and that file's
assertions are all about interpreting book events, never about the request. The browser proof
that does drive the real live parameter shape intercepts on the glob `**/bet/replay/**`, which
would still match if the segments were reordered, hardcoded, or built from defaults, and it is
unwired in any case. A silent swap of `p.mode` for a literal `'BASE'` would ship green.

### REQ-091 (NO_PROOF, MEDIUM)

The loader is real and it does cover the fetch window: `replayPhase` starts at `'loading'`, the
markup renders the loading branch first, and the phase only advances on the line after
`await fetchReplay(p)` returns. I could not find any proof path at all. Looked at: all six
committed frames under `reports/screens/replay-blocker/` (none is a loading frame),
`replayRounds.test.ts` (no `phase` reference), the ten browser legs in `checks.yml:571-599`,
and `replay_blocker_proof.mjs`, whose `openReplay` waits for `.start-replay` to be visible and
therefore skips past the loading state without capturing it. Severity MEDIUM rather than
STREAM because the loader is present and the risk is regression, not a current defect.

### REQ-093 (SATISFIED)

The platform wording allows hide OR disable, and this game hides by construction: the betting
controls are inside the `{:else}` arm, so there is no code path that renders a bet control in
replay. Two secondary guards were opened and quoted: the spacebar handler returns early on
`isReplay` (1597-1598), and `SessionPanel` is explicitly noted as living inside the non-replay
branch (2086-2088). No proof beyond the frame; a CI assertion of the shape "no betting
component appears above the `{#if isReplay}`" does not exist.

### REQ-094 (NO_PROOF, HIGH)

The `if (isReplay) return` at `App.svelte:1170` is twelve lines before the token read and
`initRGS`, so authenticate cannot run; and because replay never enters the live spin path,
`play` and `endRound` cannot run either. `replayService.ts` contains exactly one network call
and it is an unauthenticated GET to the public replay endpoint. The implementation is sound.

Nothing defends it. Note the asymmetry that makes this HIGH rather than MEDIUM: an accidental
move of the `if (isReplay) return` below `await initRGS(...)`, or one `import { spin } from
'./rgsService'` added to a replay surface, is a one-line edit that turns a public replay into
an authenticated session call. That is precisely the class the platform lists as its own
requirement, and it is gated nowhere. `App.svelte:1163` refers to "the network-hygiene gate"
as though it exists; there is no such step in `checks.yml`, which is a documentation-versus-CI
mismatch worth a row of its own.

### REQ-095 (NOT_MET, STREAM)

The animation half is genuinely complete and I want to be precise that this is not a
"reduced presentation" finding in the visual sense: replay drives the same `GameGrid`
instance through `animateSpin`, the same `FreeSpinsPresentation` overlay for feature rounds,
the same `MaxWinCelebration` wincap flow with a real COLLECT wait, and the same `WinDisplay`
count-up, all through the public `.set()` API of the locked `gameStore` writables.

The audio half is reduced, and the platform text is explicit: "Show all animations, sounds,
and results". What does fire in replay is only what `GameGrid` triggers internally
(`GameGrid.svelte:39` imports `playSpinStart, playReelStop, playAnticipation,
playScatterLand`, called at lines 935, 444-445, 515-516 and 993/1085). What does NOT fire is
the win sound, the background music and the gesture warm-up, because all three are called
from `App.svelte`'s `onMount` and live spin handlers, downstream of the replay early return.
So a reviewer replaying a 390x win watches the full celebration in silence apart from reel
stops. I did not attempt to establish whether this was a deliberate choice: no comment in
`ReplayMode.svelte` mentions audio at all, and no tracker row I opened records it, so the
honest reading is an omission rather than a decision. Escalation-worthy as a submission
surface, not fixable by me.

Proof is partial in a narrow sense only: the CI-wired `max-win hold` leg does assert one
property of the replay presentation, with a seeded self-test, and I quoted it. It says nothing
about whether animations or sounds run.

### REQ-096 (NOT_MET, STREAM)

All three figures exist in replay but never at the same time, and the one that is missing is
missing exactly where the platform asks for it: "Show results". Before the press the surface
shows the bet and, for a cost-multiplier mode, the total cost. After the press the button is
replaced and the surface shows the payout multiplier and the win amount. Frame 04 is the
results view and carries no bet cost.

Two further observations from that frame, both already on the ledger and reported as KNOWN
rather than as new: the win pod sits overlapping the reel window on the right, which is
`KNOWN(TR-114)`, the replay ghost pod; and the pod's `WIN 3900.00` carries no currency symbol
while the banner beside it reads `€3,900.00`, which is the money-display class
`KNOWN(TR-115 / TR-086)`. I did not open a new id for either.

One thing I could not establish: whether the platform means "payout" as a figure distinct from
"win amount". In this implementation they are the same money value
(`winAmount.set(microsToDisplay(response.payoutMultiplier * params.amount))`,
`ReplayMode.svelte:225`), presented once as an amount and once as a multiplier. If the platform
intends payout and win to be separable (for example cost-inclusive versus net), this row would
need re-reading against a live example.
