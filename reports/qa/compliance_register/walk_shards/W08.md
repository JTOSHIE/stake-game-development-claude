## PER REQUIREMENT NOTES

### REQ-010 to REQ-015, the six disclaimer messages: implementation good, proof absent

**What I opened.** `frontend/src/lib/i18n/prose.ts:118` carries the whole real-money
disclaimer as one key, `disclaimerBody`, and `:211` carries the social variant inside
`PROSE_SOCIAL` (`'Malfunction voids all prizes and plays. ...'`). It is consumed at
`frontend/src/lib/components/PaytableModal.svelte:62` (`$: disclaimerText = $tr('disclaimerBody')`)
and rendered at `:408-409` under the heading `{$tr('disclaimerHeading')}`, inside a block
whose own comment reads `<!-- Disclaimer (Stake Engine seven-point requirement) -->`.

**Message by message, against the verbatim platform text.** All six are conveyed, in the
project's own wording, which `R1-19` expressly permits:

- REQ-010 "Malfunction voids all wins and plays." shipped verbatim.
- REQ-011 "A consistent internet connection is required." shipped as "A stable internet
  connection is required to play."
- REQ-012 "reload the game to finish any uncompleted rounds" shipped as "If your connection
  drops during a round, reload the game to finish any uncompleted round." (singular round).
- REQ-013 shipped as "The theoretical return to player is calculated over many thousands of
  plays and does not guarantee any result in a single session."
- REQ-014 shipped as "This game display is for illustrative purposes only and does not
  represent a physical device."
- REQ-015 shipped as "Winnings are settled according to the result returned by the Remote
  Game Server, not from events shown in the web browser." The platform says "the amount
  received from"; ours says "the result returned by". Same message, different words.

**Why the proof is NONE and not EVIDENCE.** There IS a committed screenshot, and I opened
it: `reports/screens/rules-paytable-2026-07-25/09-disclaimer.png` shows the rendered
paytable with the DISCLAIMER heading and all six sentences legible, plus the studio
trademark line. It corroborates the current state, and I am recording it so the marshal has
it. It is not a proof path under this audit's own test: it is a static PNG from 2026-07-25
and deleting a sentence from `prose.ts` tomorrow would not make it, or anything else, go
red. Its own `PROVENANCE.md:9-13` makes the point for me, because its content assertions are
`PASS showsRtp`, `PASS showsMaxWin`, `PASS showsModeCosts`, `PASS showsInterfaceGuide`,
`PASS showsResponsiblePlay` and there is **no disclaimer assertion at all** in the list.

**What else I checked and ruled out as proof.**

- `frontend/scripts/locale_prose_conformance.mjs` is the only script in `frontend/scripts`
  that mentions the disclaimer, and only in comments (`:18`, `:286`). Its part 1 asserts
  presence, not content: `if (proseI18n[loc]?.[k] === undefined) failures.push({ part: 'completeness', locale: loc, key: k, table: 'proseI18n' })`
  (`:200`). Presence of the key says nothing about whether the key still carries the six
  messages. **It is also not wired into CI**: grepping `.github/workflows/checks.yml` for
  `prose_conformance` returns nothing, so it is SCRIPT_UNWIRED even for what it does assert.
  It does carry a convention (p) self-test (`:306`), which is more than several wired gates.
- `frontend/scripts/locale_completeness_check.mjs` IS wired (`checks.yml:223-225`) but reads
  `src/lib/i18n/translations.ts` only (`:24`, `const SRC = readFileSync(join(ROOT, 'src/lib/i18n/translations.ts'), 'utf-8')`),
  so the prose table, where `disclaimerBody` lives, is outside its reach.
- `reports/qa/locale_prose_conformance.json` is committed output of the unwired script;
  its per-locale rows are `"harvested": 89, "hits": 0`, i.e. prohibited-term hits, with no
  record of the disclaimer's content.

**The finding.** Six approval-mandated messages are carried by one string in one key, with
no gate, no unit test and no captured assertion anywhere. A single careless edit to
`prose.ts:118`, or a locale file whose translator dropped a sentence, ships an
approval-failing disclaimer with every check green. Not matched by any row in
`reports/qa/stream_test/KNOWN_OPEN.md`.

### REQ-017, restricted phrases anywhere in the game: satisfied, with two named blind spots

**Implementation.** The restricted-phrase table is transcribed into
`frontend/src/lib/i18n/vocabulary.ts` and applied two ways: `sv()` rewriting, and the
social prose table at `prose.ts:184-212`, which carries the social wording for every
gambling-framed key. I hand-checked the social disclaimer at `prose.ts:211` against the
platform's own list at `approval_guidelines_jurisdiction_requirements.md:24-63` and found
no restricted phrase in it ("plays", "play" and "player" are replacements or non-matches
under word-boundary matching, not restricted terms).

**Proof, and it is real.** `checks.yml:246-248` wires `vocabulary.test.ts`, whose `:132`
assertion resolves the social strings through the shipped `t()` and asserts zero prohibited
terms, and whose `:53-56` assertions rebuild the term table from the dated mirror so the
table cannot be quietly edited to make a failing string pass. `checks.yml:233-235` wires
`a11y_social_terms_check.mjs`, which extends the same table to `aria-label`, `title`, `alt`
and `placeholder` (its header records the earned case: "14 control labels shipped carrying
the restricted phrase 'bet'"). The rendered-DOM half is committed evidence rather than a
gate: `reports/qa/social_dom_conformance_2026-07-25.json` records
`"stringsHarvested": { "real": 4289, "social": 3242 }`, `"social.zeroProhibitedTerms": { "pass": true, "hits": [] }`
and seven surfaces covered including `paytable`.

**Blind spot 1, the platform's "images" clause.** The platform text says the prohibition
"potentially extends to images and UI elments". Every instrument I opened is a text scan:
`vocabulary.test.ts` reads strings and component source, `a11y_social_terms_check.mjs`
reads attribute literals, `social_dom_conformance.mjs` harvests DOM text. Nothing inspects
rendered art for baked-in words. `CLAUDE.md` asserts "front-facing symbols carry no
baked-in text", which is the design that makes the risk small, but it is an assertion and
not a gate. UNKNOWN whether any shipped raster carries a restricted term; I did not attempt
OCR.

**Blind spot 2, the CI-wired scan's key list.** `vocabulary.test.ts:116-120` enumerates
`RULE_KEYS` (six) and `GUIDE_KEYS` (sixteen), and `:128-132` scans only those. **`disclaimerBody`
is not in either list**, so the social disclaimer is covered by the committed 2026-07-25 DOM
scan and by nothing that runs on a pull request. The DOM scan itself is deliberately not
wired, which `checks.yml:243-245` states plainly: "The full rendered-DOM scan needs
Playwright and a dev server and so stays local, per this workflow's stated scope; its result
is committed as reports/qa/social_dom_conformance_2026-07-25.json". That evidence also
predates the 2026-07-28 JOB 2 move of the rules and guide into the locale layer, so it
describes an earlier tree.

### REQ-018, the social=true query parameter: satisfied, with the parameter read itself ungated

**Implementation.** `socialMode.ts:26-33` reads the parameter at module load and accepts
`true` or `1`; `:61` freezes it as `socialFromUrl`; `:73` folds it into `socialAtBoot`,
which exists so first paint is social-correct before any store write; `:87-93` derives
`isSocial` from the URL flag, the platform's own `socialCasino` jurisdiction flag and the
social currency set `['XGC', 'XSC', 'SC', 'GC', 'XEC']`, any one of which is enough. The
file's own reasoning is worth keeping: "presenting social wording to a real-money player is
a cosmetic error while the reverse is a compliance breach".

**Proof.** The phrasing half is genuinely gated and would go red: `vocabulary.test.ts:153-154`
asserts `t('en', 'bet' as never, 'social') === 'PLAY'`, and `:132` asserts the resolved
social corpus is clean, both wired at `checks.yml:246-248`. `socialLocale.test.ts` is wired
at `checks.yml:408-410` and pins the platform's social-renders-English rule across all
sixteen codes (`:54`, `eq('social + ${code} is forced to English', resolveLaunchLocale(code, true, locales), 'en')`).
End-to-end, `social_dom_conformance.mjs:258` navigates `${baseUrl}/?social=true` and its
committed output harvested 3242 social strings with zero prohibited terms, which is the one
artefact tying the URL parameter to the served phrasing.

**The gap, stated precisely.** Nothing asserts the parameter READ. `vocabulary.test.ts:162-164`
regex-checks that `readUrlCurrency` and `socialAtBoot` exist in the source, not that
`socialAtBoot` derives from `social`; no test in the 20 exercises `readUrlSocial`, which is
module-private and unexported. Changing `:29` from `v === 'true' || v === '1'` to anything
wrong would leave every CI check green, and the only instrument that would notice is the
unwired local DOM scan. Recording it as a residual weakness rather than as the row's
verdict, because the substantive obligation is gated.

**On the `sweeps_<lang>` half.** The slice is right that it is a recommendation
("We reccomend using an additional language file with the prefix: sweeps_<lang>"). This
project does not use that naming; it uses one social override table
(`PROSE_SOCIAL`/`SOCIAL_I18N`) plus the forced-English social locale. That is a different
mechanism satisfying the same recommendation, and English-only social sessions are
themselves a platform rule per `socialLocale.ts:3`, so no per-language sweeps file could
apply. Not a finding.
