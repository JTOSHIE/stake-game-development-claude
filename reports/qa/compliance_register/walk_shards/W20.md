## PER REQUIREMENT NOTES

**REQ-120.** Opened `currency.ts` in full and the platform helper `DisplayBalance` at
`rgs.md:259-278`. **What IS satisfied, and it is most of the row:** virtual codes render
`10.00 SC` / `10.00 GC` trailing exactly as the platform's table shows, `XEC` is defined
byte-identical to `XSC`, zero-decimal currencies drop the decimal point, fiat symbols come
from `Intl` with `currencyDisplay: 'narrowSymbol'` keyed on the code the platform sent, and
all of that is asserted by a CI-wired test. **What is NOT satisfied is the clause the
requirement names explicitly.** The platform's helper defaults an unrecognised code to
`{ symbol: balance.currency, decimals: 2, symbolAfter: true }` and therefore renders
`1.00 ZZZ`; `currency.ts:223` renders `ZZZ 1.00`. Confirmed against the platform source,
not inferred. **Reachability, stated so the tier is honest:** `Intl.NumberFormat` resolves
a narrow symbol for every ISO code in the platform's `Currency` union, so this branch
fires only on a code that is not a valid ISO currency at all. LOW. **A second, latent
divergence in the same file:** on the leading-placement branch `currency.ts:194` emits
`` `${symbol} ${formatted}` `` with a space where the platform helper emits
`` `${meta.symbol}${formattedAmount}` `` with none, and `currency.test.ts:116` pins the
spaced form. That branch is currently unreachable in production: I grepped every
`formatBalance(` call site in `frontend/src` and **none passes the fourth `display`
argument**, so the `CurrencyDisplay` path is dead code today and every player-facing string
comes from our own table plus `Intl`. **What I could not establish:** I read the `Currency`
union and the head of `CurrencyMeta` but not the full per-currency record body at
`rgs.md:204-257`, so I have NOT verified our `ZERO_DECIMAL` set (`JPY IDR KRW VND CLP`)
against the platform's own `decimals` for every one of its ~50 codes. That check is open.

**REQ-121.** This is the sharpest finding in the slice. Every non-locked bet mutator
lives in `betLadder.ts` and constrains the bet to membership of `activeBetLevels`; none
of them reads `minBet` or `maxBet`. The locked `rgsService.authenticate()` parses both
into its `AuthResponse` (`rgsService.ts:565-566`) and then drops them: `initRGS` publishes
only `rgsBetLevels` and `jurisdictionFlags` (`rgsService.ts:735, 738`), so no non-locked
code can see the limits. **The concrete hole is the fallback.** The platform's own lead-in
says bet levels are not mandatory, so an authenticate response may legally carry an empty
`betLevels`; `activeBetLevels` then falls back to the hardcoded `BET_LEVELS`
(`betLadder.ts:39-41`), which is a USD-shaped `[0.10 ... 100.00]` ladder with no
relationship to that session's `minBet`/`maxBet`. On a high-minimum currency the player
would be offered, and could submit, a bet the RGS must reject. I could not find any
guard, test, gate or tracker row covering this; I looked at both bet tests, the contract
test, the whole of `checks.yml`, and grepped the tracker and charter. Severity HIGH rather
than STREAM because reaching it needs a platform config we do not hold, but a player in
that session would see it.

**REQ-122.** The implementation argument is genuine and is written out in the source
rather than asserted: nothing synthesises, rounds or interpolates an amount, so every
submittable value came out of the platform's own `betLevels`. `betLadder.test.ts:80`
(`check('every guard refuses to act off ladder', ...)`) and `betSelector.test.ts:93`
(`check('a value from the PREVIOUS ladder is refused once the ladder changes',
setBetLevel(7_500), false)`) both pin the membership discipline. But **no assertion
anywhere mentions `stepBet`**, and the tracker records exactly why: TR-095 parks the
stepBet assertion with a named one-line lock sanction request against `rgsService.ts`.
So the proof for this requirement as the platform words it is the tracker row, the
weakest form, and it is the right form here because the item is genuinely parked.
**Two weaknesses worth recording.** First, `betSelector.test.ts` is NOT wired into
`.github/workflows/checks.yml` at all (grepped: zero hits for `betSelector`), so the
strongest membership assertions in the repository are not defended by CI; the same is
true of `roundInterpreter.test.ts` and `roundInterpreter.determinism.test.ts`, three of
the twenty test files. Second, the empty-`betLevels` fallback described under REQ-121
bypasses the by-construction argument entirely: the hardcoded ladder is not derived from
`stepBet` either.

**REQ-124.** The only bet ladder the product itself defines is `BET_LEVELS` in the LOCKED
`gameStore.ts`, floored at 0.10, and `betLadder.test.ts` treats that floor as expected
behaviour. Live sessions get the platform's ladder, so the game does not itself block a

submissions should incorporate small denomination bets"), and nothing in this repository

**REQ-125.** Derived before measuring, per convention (l.1). The minimum paytable entry is
`(3, "L3"): 0.08` at `games/future_spinner/game_config.py:127`, which is below 0.1x, so the
platform text requires 4 points of precision. The single money formatter hardcodes 2 (or 0
for zero-decimal currencies) and every win readout goes through it: `HudOverlay.svelte:366`
for the HUD, `WinPod.svelte:14-15` for replay. No 3-place or 4-place path exists anywhere in
`frontend/src`. I did not enumerate every win surface in every layout profile, so I cannot
say how many readouts are affected, only that all of them share this one formatter.
STREAM because at the current $0.10 floor a 0.08x win is $0.008 and renders as `$0.01`.

**REQ-126.** Downstream of REQ-125 and reported separately rather than folded in, because
the marshal clusters across tiers. There is no bet-size input to any money formatter:
`formatBalance(micros, currencyCode, localeTag, display)` has no bet parameter and
`HudOverlay.svelte:366` passes none, so a bet-conditional precision rule cannot exist
today. Graded LOW on its own because with no extra precision anywhere the game does not
VIOLATE the "only below $0.10" recommendation; it simply has no mechanism to comply with
the parent obligation. The finding of substance is REQ-125 and REQ-127.

**REQ-127.** This is the row where the platform text is strongest ("it is only a requirement
that wins in-game show exact win amounts") and it is the row the code fails most plainly.
`maximumFractionDigits: decimals` with `decimals = 2` is a rounding instruction, so a
0.008 win reads `$0.01`, which OVERSTATES, the direction `currency.ts:239-242` itself argues
is forbidden: "TRUNCATION, not rounding, and this is a money rule rather than a style
preference. Rounding to nearest renders a balance of $999,999.99 as "$1M", telling a player
they hold more than they do. Truncating renders "$999.9K", which can only ever understate."
The same file therefore holds the correct principle for compact values and the opposite
behaviour for exact ones. I checked `KNOWN_OPEN.md` for a match: the
nearest rows are TR-115/TR-086 (money display FIT failures) and C-20 (the balance readout
claim, CLOSED as not a defect), and neither is this. A grep of `LEDGER.md` for
"precision"/"decimal" returned one hit, `WinPod.svelte:6`'s multiplier precision, a
different quantity. Reported as new, at STREAM.

**REQ-128.** Satisfied and doubly proved. `spinCostMicros` is the one integer-micros cost
source, `modalGuard.test.ts` asserts the per-tier multipliers and the affordability
arithmetic at exactly the price boundary, and `fsModes.drift.test.ts` asserts the frontend
multipliers equal the shipped maths package's `index.json` costs, so a drift between the
displayed price and the served mode fails CI. Both steps are wired. The game correctly
sends the BASE amount and the mode and lets the wallet apply the multiplier, which is what
the platform text describes.

**REQ-129.** Satisfied. The request body is exactly `{sessionID, mode, amount}` with a
