## PER REQUIREMENT NOTES

### REQ-097 (SATISFIED, with two weaknesses worth recording)

The control exists and a live frame shows it. I graded EVIDENCE rather than NONE because the
requirement is existential ("Add a Play Again button"), and a captured live frame showing the
control is direct proof of an existential claim in a way it could never be for a universal one.

Two weaknesses, neither changing the verdict:

1. **No gate holds it.** `frontend/scripts/replay_blocker_proof.mjs:156` does assert the control
   appears, `await page.locator('.play-again').waitFor({ timeout: 20000 })`, and that
   script carries a real convention (p) seeded pass ("seeded interception goes red"). But it is
   **SCRIPT_UNWIRED**: I read every `- name:`/`run:` pair in `.github/workflows/checks.yml` and
   `replay_blocker_proof.mjs` appears in neither the static-gate step list nor the ten-entry
   browser matrix. Delete the button and CI stays green.
2. **Nothing asserts the restart, only the button.** `playAgain()` sets `phase = 'ready'`, which
   re-renders the `.start-replay` button, so rewatching takes TWO presses (REPLAY AGAIN, then
   START REPLAY). The proof script never clicks `.play-again`, so the second half of "Allow
   rewatching the replay" is unexercised anywhere. Also, `playAgain()` resets `activeWins`,
   `winAmount`, `isWincap` and `scatterCount` but not `boardSymbols`, `isSpinning` or
   `featureScript`/`featureActive`, so a second run starts with the previous board still set.
   Not observed as a defect; recorded as untested surface.

The frame I opened also re-shows two already-recorded rendered-surface findings, so they are not
new: the un-formatted `WIN 3750000.00` (no separators, no symbol) is **KNOWN(TR-087)** and
**KNOWN(TR-115 / TR-086)**, and the legacy MULTIPLIER/WIN pod mounted over the stripped replay
view is **KNOWN(TR-114)**.

### REQ-098 (NO_PROOF)

The error state is genuinely implemented, in both directions: the fetch leg throws with a status
message at `replayService.ts:133-137`, and `ReplayMode.svelte`'s `onMount` catch and its
`startReplay` catch (`:247-253`) both set `phase = 'error'` and publish to `replayError`. The
template renders a titled, detailed error block, so a failed fetch is neither a blank screen nor
a silent hang. The English strings are locale routed (`$tr('replayFailed')`), which supersedes
the stale `docs/QUALITY_CHARTER.md:359` row that still lists `Loading replay…` and
`Replay failed to load` as hardcoded English at "`ReplayMode.svelte:269, 272, 299, 309`" (those
line numbers no longer hold; the strings at :289 and :292 are `$tr(...)`). The one survivor from
that charter row is `Mode:` at `:319`, which is **KNOWN(Q-16 park)**.

**What is missing is any proof at all.** Nothing in the repository exercises the failure branch.
The one browser proof for replay stubs `**/bet/replay/**` with a successful `route.fulfill`, so
it can never see a 404, a 500 or a network drop. Gate 13's source scan checks the legacy event
search has not returned and says nothing about `phase`. There is no tracker row and no committed
frame of a failed replay. Someone deleting the `{:else if phase === 'error'}` branch, or
narrowing the catch, would ship a blank replay screen with every gate green. That is the finding.

**One quality observation while in the file, tiered LOW and not suppressed.** The player-facing
`.error-detail` prints `e.message` verbatim, which for a failed fetch is
`Replay fetch failed (404 Not Found). URL: https://rgs.stake-engine.com/bet/replay/<uuid>/1/BASE/5`.
A raw endpoint URL and an HTTP status shown to a player reads as machine-generated output, which
the standing mandate names directly ("Nothing player-visible may read as machine-generated"). Not
in KNOWN_OPEN.md and not in the charter's machine-tell tables that I read, so possibly new; I did
not search the 571-row `reports/qa/stream_test/LEDGER.md`, so treat it as unconfirmed-new.

### REQ-099 (NO_PROOF)

The implementation is real and I opened all three legs of it: the whole non-replay UI sits in the
`{:else}` arm at `App.svelte:1692`, so no bet ladder, balance readout, autoplay panel or spin
control is even instantiated in replay; `App.svelte:1170` returns before any RGS initialisation;
and `App.svelte:1598` makes the spacebar-to-spin handler inert. `replayService.ts` imports nothing
from `rgsService` and its only network call is `fetch(url)` against `/bet/replay/...`.

I marked proof NONE rather than EVIDENCE deliberately, and this is the judgement call in this
shard. The requirement is UNIVERSAL: "No control or path anywhere in replay mode can begin a real
money session." A single live frame showing no controls is consistent with that but cannot
establish it, and there is nothing else: no CI step, no test among the 20, no source scan, no
tracker row. `round2_review3.md:96` records "Hide normal betting controls and prevent normal-play
transition | PASS in source | Replay has a separate UI branch", which is a reviewer's reading of
the source and not a gate (and that file is not `REVIEW_TRACKER.md` or `QUALITY_CHARTER.md`, so it
does not qualify as TRACKER_ROW under this walk's definition either).

**The cheap gate this is missing**, recorded because it is one assertion: gate 13 already reads
`ReplayMode.svelte` as text and asserts the absence of four patterns. A sibling assertion over
`App.svelte` that the replay branch is `{#if isReplay}<ReplayMode />{:else}` and that
`ReplayMode.svelte` contains no `rgsService` import and no `spin`/`play` call would close this
class in the file that already does exactly this kind of scan.

### REQ-160 (NOT_MET)

Two documents claim this deliverable and they disagree with each other and with the committed
fixture.

`REPLAY_TEST_EVENTS.md` is the substantive one: 25 cells, five modes across five scenarios, IDs
derived from `lookUpTable_<mode>_0.csv`. Twenty-two cells hold an ID. Two hold a defended `n/a`
(`Loss` for `bonus` and `super`, because a bought guaranteed trigger has no zero-payout outcome,
and the row says to tell the reviewer so, which is the right answer to the platform's own
"if applicable"). **One cell does not hold an event ID at all**: base-mode `Feature trigger` reads
`*see method*`, and base is the mode a reviewer is most likely to ask about, since it is the only
mode where the bonus trigger is a rare organic event rather than purchased.

**That gap is already closed in the repository and only the document has not caught up**, which is
what makes this actionable rather than open research. The committed fixture
`frontend/src/lib/services/__fixtures__/replay_rounds.json`, extracted from the shipped books by
`frontend/scripts/extract_replay_fixtures.mjs`, holds `base.feature = { id: 1, payoutMultiplier:
36389, criteria: "freegame" }`. Base sim 1 is a `freegame` round. `REPLAY_TEST_EVENTS.md:28`
already lists `**1** (~363.89x)` as base's Big win, and 36389/100 is 363.89x, so it is the same
round: base sim 1 is a trigger-plus-big-win, exactly the coincidence the document already
describes in prose for cruise sim 11 and antelite sim 1 at :31. The document says base's trigger
is unpinned while CI has been replaying it every run.

The second document, `docs/REVIEW_EVENTS_PLAN.md`, is worse against this requirement and should
not be handed to anyone as-is: all eleven rows have both ID columns empty, and its Mode column
uses only `base` and `bonus`, so three of the five shipping modes never appear. Its own line 3
frames it as a capture sheet ("Event IDs to capture on the deployed staging build, then fill into
the ID column"), which is fair, but a reviewer asking for per-mode IDs would be handed an empty
grid.

**What the CI gate does and does not prove.** `checks.yml:420-422` is genuinely wired and the
assertions are real, so the round CATEGORIES demonstrably replay. But the fixture covers all five
categories only for `base`, `cruise` and `antelite`; `bonus` and `super` carry `cap` and `feature`
only. So `bonus` normal win (doc: 130), `bonus` big win (doc: 0), `super` normal win (doc: 1484)
and `super` big win (doc: 0) are four reviewer-facing IDs with no gate behind them. And the gate
proves categories, not identities: nothing anywhere checks that the specific IDs in
`REPLAY_TEST_EVENTS.md` resolve to the rounds the table claims, which is compounded by the
document's own honest `sim_id` off-by-one caveat at :42-44 ("the deployed RGS event ID may be
offset by 1 - **verify each ID against the staging build**"). No convention (p) self-test exists
for gate 13 either: `checks.yml:420-422` has no `--self-test` leg, unlike the dash, machine-tell,
asset-reference, splash-calm, turbo, paytable, scrim, count-up, max-win-hold, bet-selector and
preview-server gates, all of which pair one.

### REQ-161 (NOT_MET, half discharged)

The max-win half is done properly and I verified it by opening the frame rather than trusting the
filename: `super` event `22975` was replayed on the live platform through the real replay endpoint
and reached `MULTIPLIER 5000.0x` with `WIN 3750000.00`, and the companion frame captures the
`MAX WIN REACHED` overlay with its COLLECT. `REVIEW_TRACKER.md:234` (TR-076) records both and calls
the surface "**RESOLVED, CONFIRMED LIVE**". That is exactly what the requirement asks for on the
max-win side: exercised, and recorded.

The rare-feature half is not discharged, and cannot be as the record stands. The rarest feature
this game has is the base-mode Overdrive trigger, 1 in 184.7 per `CLAUDE.md`'s own facts block, and
the 5-scatter variant is rarer still; `REPLAY_TEST_EVENTS.md:31` has no event ID for it, so no live
replay run against it can exist. The feature replays that ARE evidenced are `super`, where the
trigger is bought and guaranteed, so they exercise the presentation but not a rare event ID. There
is no committed frame of a base-mode trigger replaying on the platform: the only other live replay
capture I found is `reports/screens/dtt-live-2026-07-26/37_REPLAY_WORKING_event_52121_with_disclaimer.png`,
whose sibling `36_bet_detail_event_52121_replay_this_bet.png` names it a bet-detail replay of event
52121, and `replay_blocker_proof.mjs` treats 52121 as its BASE WIN case, not a trigger.

Also unrecorded: `REPLAY_TEST_EVENTS.md:85-88` item 3 asks to confirm "max-win (5,000x) replays and
dwells in **every mode**". The evidence covers `super` only, i.e. one of five, and the checklist is
committed still in its unticked pre-staging state with no dated completion note beside it.
