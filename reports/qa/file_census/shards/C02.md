## NOTES

**On the allowlist audit, the squad's named task, and the two questions it hides.** The
brief asks whether the allowlist still matches reality, and that is two separate
questions which have different answers. First: does every allowlist key name a store that
actually exists? Yes. All thirteen resolve to a real `export const` at a line I opened, so
there is no phantom entry and no rename has orphaned a key. Second: is every allowlisted
store still dead? No. `activeRound` is read at `App.svelte:575` through `get()`, one of the
five forms the scan's own `isReadIn()` recognises at `dead_wiring_scan.mjs:117-123`, so the
store resolves ALIVE, is never placed in `dead`, and its entry sits there carrying a reason
that HEAD contradicts. The entry says the consumer is a parked question awaiting a DTT
session; the consumer exists and the comment three lines above the read attributes it to
TR-099. Nothing is broken by this today, which is precisely why it is worth recording: it
is a tooth that has already rusted, and the file has no mechanism that could ever say so.
The fix is one loop mirroring the `EXPECTED_ALIVE` block already in the file: fail when an
allowlist key is absent from `dead`. **I did not verify what the gate PRINTS**, because
that would mean running it and it writes; the conclusion is derived entirely from reading
the filter at line 144 and the read forms at 117 to 123, which is sufficient for it.

**On the Q-26 undercount, and why the number matters more than the finding.**
`KNOWN_OPEN.md:20` says four prose and config instances remain open and locates them in
`prose.ts`. The location is now right and the count is wrong by roughly ten times. The
English master carries three (`1.6x` and `1.25x` in `modeOverboostBlurb`, `5x` in
`modeSuperBlurb`); `PROSE_SOCIAL` repeats all three, because those two keys happen to be
among the ones whose wording changes in social mode; and all fifteen non-English locales
repeat all three again. Fifty-one. The row's own recorded lesson was that its instrument
searched two file types and missed a third, and the same instrument evidently searched the
master table and not the locale table. The corroborating detail, which is what convinced me
this is mixed glyphs rather than a lagging translation, is that `prose.locales.ts` carries
45 correct `×` characters alongside its 45 letter-`x` characters: every locale block is
internally inconsistent in the same way, so this is one editorial decision propagated
sixteen times, not fifteen translations that fell behind. I have NOT claimed which frames
render these strings, because I opened no frame; they are mode blurbs and their surfaces
are named in the already-open row. Sizing the class correctly changes the fix from a
one-line edit to a 51-instance sweep across sixteen locales, which is exactly the kind of
misestimate `KNOWN_OPEN.md:15` records TR-104 making in the other direction.

**On the `CURRENCY_SCALE` claim, and the honest limit of the finding.** CLAUDE.md and the
gate both state there is exactly one declaration in the codebase. There are two:
`utils/currency.ts:35` and `frontend/scripts/qa_soak.mjs:47`, both `1_000_000`. Whether a
dev soak harness counts as "the codebase" is arguable, and I state plainly that it is
arguable rather than pretending it is not. Two things make it worth a row anyway. The gate
declares its own intent more broadly than its implementation delivers: it says a consumer
that grew "a copy under another name" is what it watches for, but it opens three hardcoded
files and never walks the tree, so it could not find a copy anywhere else however
egregious. And `qa_soak.mjs` uses its copy to compute money verdicts over a 25 to 30 minute
soak, so a divergence there would produce a wrong soak PASS rather than a wrong player
balance. The values agree at HEAD, so there is no live drift and no player-visible defect;
the defect is that a gate prints "no copies" while a copy exists, and per convention (p)
that is an unverified claim rather than evidence. I did not run the gate.

**On why every test file is tooling, argued rather than asserted from the extension.** The
easy move is to say a file under `frontend/src` is in the shipped tree, therefore skin.
Two pieces of evidence in scope say otherwise and neither is a filename inference. The
shipped-code scanner partitions this exact tree into `production` and test by the `.test.`
infix and reasons only about the former, so the project's own tooling already treats the
split as meaningful. And `fsModes.drift.test.ts` carries an `npx tsx` command line in its
header, reaches outside `frontend/` into the locked maths package, and exists to compare a
config against a generated artefact. That is a gate. The `__fixtures__` JSON files follow
it: they have no production reader, and their directory name is the vitest convention.

**On `mock/`, the one genuinely arguable class in scope.** It is imported from production
source three times, so a naive read makes it skin. But every import is a dynamic
`import()`, its own first line declares it an offline mock, four separate scripts under
`frontend/scripts/` reason about it, and one exists specifically to assert that
`mock/roundProvider` and `mock/sample_rounds` do not appear in the shipped artefact. A file
whose containment in `dist` is a gated invariant is not part of the shipped skin. **I have
NOT verified that the containment gate passes**, because running it is out of bounds; I rely
on the gate's declared intent plus the module's own header. If a later pass finds the mock
actually shipping, that is a different and far larger finding than a misclassification, and
this row should not be read as evidence against it.
