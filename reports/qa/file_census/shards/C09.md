## NOTES

**On the answer to "should they be under `reports/screens/`".** Yes on the convention, and the
convention is unambiguous: CLAUDE.md (h) says a pass that changes what renders commits proof
"to `reports/screens/<pass>/`", and v7 (h) says the same with a stated reason, "superseded
artefacts are explicitly marked or archived, never left ambient (a stale HANDOVER once cost a
2-star external audit misread)". These 21 sit outside that tree, in the frontend source tree,
undated, unindexed and with no `<pass>` directory to say which pass produced them or when.
The dates on disk run 2026-07-07 to 2026-07-25, so they are proof for at least four separate
passes flattened into one directory. That is the misfiling; the files themselves are real
evidence, correctly produced, and none of them is dead.

**On whether they ship, answered by reading rather than by the `public/` heuristic.** The
census's own hedge, that `public/` is copied verbatim and `screens/` is not, is correct but is
an assumption until the config is opened. Opened: `vite.config.ts` sets `publicDir` nowhere, so
it stays at the default `<root>/public`; sets `rollupOptions.input` nowhere, so `index.html` is
the only entry; and its one custom plugin, `pruneLegacyAssets`, only ever deletes. There is no
`viteStaticCopy`, no `fs.cp`, no glob import in `frontend/src` that could reach a PNG two
directories up. The built tree agrees: four entries, none of them `screens`. So the answer is
no, and the 21 PNGs cost the repository 15MB rather than costing the bundle anything.

**On the h.1 instance, and why it is a contradiction rather than a fresh discovery.** The rule,
its history and its enforcement helper are all committed: `evidencePaths.mjs` exists precisely
because five scripts were found writing into committed evidence under `reports/screens/`, and it
says so in its own header. Every one of the five scripts producing this scope's files still
builds its output path by hand and points it at a committed directory, and none imports
`evidenceDir`, so the helper's coverage stops at the tree it was written for.
`symbol_life_proof.mjs` is the softest of the five, because its path is an argument and only its
default lands in `screens/`, but the default is what a bare `node scripts/symbol_life_proof.mjs`
uses. I did not run any of them, so I am asserting what the code does, not what a run did: in
the other four the write is unconditional, `mkdirSync` on the committed directory at module
scope followed by `page.screenshot({ path: join(OUT, '<committed name>.png') })`. The h.1 record
lists the `reports/screens/` cases and this second tree is not on it, which is the useful part:
migrating the gate writers to scratch paths is recorded as open work, and this scope adds five
files to that work item.

**On the orphan list having false negatives as well as false positives.** The wave has been
warned twice that a zero in `orphan_candidates.txt` means "no literal reference found" rather
than "unused". The reverse hazard is not recorded anywhere and cost this squad its clearest
finding: `frontend/README.md` has no reference of any kind, and it is NOT on the candidate
list, because the scan matches basenames and `README.md` is one of the most-named basenames in
the tree. Any file whose basename collides with a common one is invisible to the orphan scan by
construction. `frontend/index.html` is in the same position and is genuinely referenced, so the
shield is not always wrong; that is exactly what makes it hard to see. The marshal should treat
the 550 as a lower bound on candidates, not an enumeration.

**On the two root handovers, and the reading I rejected.** Two Fable handovers dated the same
day, one with a `c` suffix and no `b` anywhere in the tree, reads immediately as a convention
(j) violation, a fresh document per update. It is not. The older opens with a three-line
supersession banner naming the newer, the newer names what it supersedes, and v7's session-start
protocol says to read "the newest living handover in the root", which resolves to exactly one
file. The missing `b` is not evidence of a deleted file: nothing references a
`HANDOVER_2026-07-25b_Fable.md` and the `c` suffix is plainly a same-day arc counter. I looked
for the mechanism before calling it a defect, and the mechanism is fine.

**On what I did not resolve.** The generator of `CENSUS_MECHANICAL.md` is not in the tree: a
search for scripts naming `CENSUS_MECHANICAL` or `orphan_candidates` found none, and the header
credits "the main loop" rather than a committed script. So C09-01, the 23-versus-21 arithmetic,
cannot be traced to a rule and I cannot say whether the path rules themselves miscounted or the
prose was written by hand over a correct list. The path rules' own logic is likewise unreadable,
which is why I cannot explain why `CLAUDE.md` and `README.md` at the root were classified while
`CLAUDE_PROJECT_INSTRUCTIONS_v7.md` and the two handovers were not; the three unclassified root
files have no property in common that the other eighteen root files lack. UNKNOWN, stated as
such.
