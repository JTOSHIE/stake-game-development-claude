## NOTES

**On C01-01, which is the only finding here I would defend hard.** The tempting version of this
row is "a document names a deleted component", which is the shape TR-006 already closed and
which would be worth almost nothing. What makes it different is the dating, and the dating is
why I ran `git log -L` rather than stopping at the grep. The line was not written while
`ControlBar.svelte` existed and then left to rot: it was written on 2026-07-13, five days after
the deletion, by a commit whose own subject says "re-validation with dated evidence, fix stale
summary line". So the evidence was false at the moment it was recorded as re-validated, in the
document that is the project's live compliance record, for the rule the gate script itself calls
"the platform manual's only hard autoplay rule". It then survived the 2026-07-27 pass whose
commit subject is "the three root documents brought to HEAD". The underlying BEHAVIOUR is
correct and I am not claiming otherwise: there is exactly one `isAutoPlay.set(true)`, it is in
`HudOverlay.svelte:192`, and the gate holds it. What is wrong is the record, and the record is
what a reviewer reads. I tiered it HIGH rather than MEDIUM on the standing mandate's inspection
test, while noting it is not player-visible and so is not STREAM.

**On the reachability claim, and why I did not trust the first pass.** My first grep for
references to the four apparently unimported components was truncated by `head -12` on the
`BetSelector` case, and the twelve lines it returned were all i18n keys, which read exactly like
"no real reference, this is a decoy match". That would have produced a confident wrong orphan
finding. The real import was line thirteen. I re-ran without the truncation and built the whole
component-to-component edge list in one pass instead of per-file, which is what C01-02 rests on.
Recording the near-miss because the failure mode is the one this wave has already produced twice:
a search that could have returned something and did not, for a reason inside my own instrument
rather than inside the tree.

**On C01-04, and testing the instrument before believing its zero.** A resolver that reports
"all 198 imports resolve" is worthless if it silently treats an unresolvable path as fine. I
seeded the exact defect the check exists to catch, in the form it would really occur, by asking
it to resolve `./lib/components/ControlBar.svelte` from `App.svelte`, which is a path this
repository genuinely used to have. It printed MISSING. Only then did I record the zero. The
resolver understands `.svelte`, bare, `.ts`, `.js` and `dir/index.ts` forms; it does not
understand path aliases, and there are none in scope, since every specifier in these files is
relative.

**On C01-08 and what I deliberately did not claim.** I can prove `c1preview.html` is not a build
input, because `vite.config.ts` has no `rollupOptions.input` and Vite's default is the root
`index.html` alone, and `fresh_eyes_review_2026-07-26.md` A8 independently confirmed `dist/`
contains exactly one HTML file. I did NOT verify the current `dist/` myself, because that needs a
build and this is a read-only pass, so the "exactly one HTML file" half is cited to that record
rather than asserted fresh. The class call, skin to tooling, is mine and rests only on the two
source comments and the config.

**On C01-13, and why it is LOW rather than higher.** The instinct is to call a submission-facing
compliance report citing a deleted file a serious defect. The dating disciplines that: the
reports predate the deletion, so nobody recorded a false thing, and the ordinary answer for a
dated report is that it ages. The residue that is genuinely a finding is narrower and is what the
row says: `audit/` has no archive marker and the headers have no date, so the snapshot property is
invisible to a reader. That is a labelling gap, and LOW is the honest tier for it. I have not
checked the other six reports in `audit/` for the same pattern, so treat the row as covering the
three I opened.

**What I did not examine, stated so the coverage is not overread.** I read the import graph, the
markup instantiation counts and the tier constants across all 25 components, but I did NOT read
the bodies of the large components (`HudOverlay.svelte` at 115KB, `GameGrid.svelte` at 76KB,
`FeatureMenu.svelte` at 55KB, `PaytableModal.svelte` at 41KB, `FreeSpinsPresentation.svelte` at
40KB, `WinBanner.svelte` at 28KB) beyond targeted greps. Any content-level defect inside those
files is out of this census's reach and UNKNOWN from here. My sampling basis for content was: the
tier-threshold constants, because they are the generator contract for committed evidence; the
`isAutoPlay` call sites, because a document contradicted the gate about them; and every relative
import specifier, because that is the mechanical "config names something absent" check the census
asks for and it is cheap to do exhaustively.
