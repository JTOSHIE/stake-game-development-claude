## NOTES

**Why C04-07 is filed rather than shrugged at.** My brief asks me to name every file whose
mechanical class is wrong. The mechanical census does not publish a per-file class, only six
totals and the 27 names it refused to guess at, so the input cannot be diffed the way the
brief assumes. Rather than infer a class from a directory name, which is the exact move this
wave has already punished twice, I derived it: the `skin` total is 1249 and `git ls-files`
gives 94 for `frontend/src`, 1019 for `frontend/public` and 136 for `design-system`, summing
to 1249 exactly. Three summands hitting the published total to the unit is strong enough to
state that every file in my scope was classified `skin`. The marshal should note that any
squad asserting a mechanical class for an individual file is either doing this same
arithmetic or guessing, and the two are not the same thing.

**The orphan verdicts rest on one mechanism test applied uniformly, and on the scan's
matching rule.** The refuted theory in `CENSUS_MECHANICAL.md` is that `assetBase` composition
hides references. That is true, but composition has a SHAPE, and the shape is one segment:
`themeStore.ts` builds `${b}/symbols/h1.png`, `${b}/ui/logo.png`, `${b}/frames/frame-2.png`,
`${b}/backgrounds/bg-1.jpg`, `${b}/sounds/*.mp3`, and `b` is one of six literal strings in
`themes.ts` that contain no `concepts` segment. A `concepts/concept-D/symbols/` path is
therefore not reachable by that mechanism, and no glob load, dynamic import or computed
CSS `url()` in scope reaches it either. The second half of the reasoning is why the scan
listed these and not their siblings one level up: the scan matches basenames, the shipped
theme files are named `h1.png` and `logo.png` which appear literally in `themeStore.ts`, and
the concept files are named `t5b_h1.png` which appears nowhere. I tested that on a real name
rather than assuming it: `grep -rl "t5b_h1.png" .` returns no lines. That single check is
what turns 402 candidates into 402 confirmations.

**None of the confirmed orphans is a ship defect, and I want that said plainly**, because a
long orphan list invites the wrong fix. `vite.config.ts:160-165` deletes
`assets/themes/{beautiful-game,oil-and-fire,trap-lane,source}` and `assets/symbols` from
`dist` wholesale, so every file in C04-12, C04-13 and C04-14 is repository weight only. The
player-visible severity is nil. What remains is what an external reviewer concludes from a
tree carrying 402 unreachable concept images, and that is a judgement for the owner, not a
defect for me to tier upward.

**C04-17 is the one finding here I would defend under a hostile read, so here is what I did
and did not establish.** Established: the two files differ in bytes, differ in pixels
substantially (57 per cent of channel bytes, max delta 117), share dimensions and colour
mode, landed in one commit, and the committed generator writes only to the design-system
path. Also established: no PNG optimiser exists anywhere in the tree, so "it was squeezed on
the way in" has no mechanism behind it. NOT established: which of the two is the intended
artwork, or whether a player would notice. I did not compare them visually and I am not
claiming a rendering defect. The claim is narrower and I think harder to dismiss: the
shipped brand mark cannot be reproduced by the recorded generator, while two committed
documents state that it is that generator's output. The 32 rung being byte-perfect in the
same commit is what makes an accident more likely than a deliberate unrecorded step.

**On provenance completeness, which is the question my brief actually asked.** Every
generation note in scope names a generator, and every named generator exists and is tracked
(C04-05). Every note stating a shipped hash states one that matches the committed bytes
today (C04-01 through C04-04). Exactly one provenance names a source that is gone from the
repository, and it is gone for a defensible reason: `bg_improved_v1.jpg` was re-encoded on
ingest, so the supplied bytes were never committed, and the note's pointer to commit
`6eaea1a` leads to the re-encodes rather than to the originals (C04-19). By contrast the
tile and the scene pair are byte-identical to their supplied sources, so for those the
source IS retained, in `design-system/brand/tile/` and `design-system/incoming/`
respectively. The class of asset with NO generation note beside it is the bulk of
`frontend/public/assets/themes/future-spinner/`, whose derivation table lives at
`docs/RESKIN_BOUNDARY.md:164-182` instead; that document classifies each file by how it was
produced and names `scene_car.png` and `scene_character.png` as "**SEMI-ORPHANS**" that
"were placed rather than derived", which is consistent with what I measured. I record that
as a location difference from the shape `CLAUDE.md` names as the model, not as a gap.
