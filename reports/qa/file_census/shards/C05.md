## NOTES

**Why almost every Python orphan candidate is false.** The scan's own disclaimer says it
matches "a file basename or full path literally in any tracked text file, plus an import-stem
form for ts, mjs, js and svelte". Python is not in that list. A Python import writes
`src.state.books`, not `src/state/books.py`, so the basename `books.py` never appears. I found
three distinct shapes it misses, all present in this scope: the absolute dotted form
(`from src.state.books import Book`, `src/state/state.py:10`), the relative form
(`from .get_pay_splits import (`, `utils/game_analytics/retrieve_game_information.py:6`) and
the bare sibling form (`from forcetool_ids import ForceTool`,
`utils/search_tool/forcetool_example.py:3`). Twenty-four of the thirty candidates in my scope
die on one of those. The marshal should assume the same for any Python candidate in another
squad's scope that has not been individually opened.

**The live maths chain, opened not inferred.** `games/future_spinner/run.py` imports exactly
seven things (lines 34 to 40). Following them: `game_config.py` pulls
`src.config.{config,distributions,betmode}` and `betmode.py:1` pulls `src.config.constants`;
`gamestate.py:22` pulls `game_executables/game_calculation.py`, which at lines 51 to 53 pulls
`src.executables.executables`, `src.calculations.ways` and `src.events.events`;
`executables.py:1-2` pulls `src.state.state_conditions` and `src.calculations.tumble`;
`tumble.py:3` and `ways.py` pull `src.calculations.board`, which pulls `src.state.state` and
`src.calculations.statistics`; `state.py:7-11` pulls `win_manager`, `symbol`,
`output_filenames`, `books` and `write_data`; `ways.py:6` pulls
`src.wins.multiplier_strategy`; `events.py:4` pulls `src.events.event_constants`;
`run_script.py:5` pulls `src.config.paths`; `write_configs.py:9` pulls
`utils.analysis.distribution_functions`; `run_analysis.py:9-10` pulls
`retrieve_game_information` and `print_all_results`, which pull `get_pay_splits` and
`get_symbol_hits` relatively. Not reachable from `run.py` at all:
`src/calculations/{cluster,lines,scatter}.py`, `src/config/optimization_paramaters.py`,
`src/write_data/force.py`, all twelve `utils/` developer CLIs, all of `uploads/`, all of
`tests/`. That is the engine-versus-inherited-surface split this squad was asked for.

**cluster, lines and scatter are inherited but not dead.** I have NOT called them orphans.
Each is imported by its own pytest module, and `Makefile:42` runs `pytest tests/`, so there is
a real mechanism. The finding about them is narrower and I have kept it narrow: they are
upstream paytype implementations that the shipped ways game never loads, and three quarters of
the committed test suite tests them. Deleting them would break `make test`. Recorded as
inherited surface, not as removable.

**Two genuinely dead modules, and I state the limit of the claim.**
`src/config/optimization_paramaters.py` and `src/write_data/force.py` are the only two files
in `src/` with no reachable importer and no call site anywhere. For both I checked the module
name, the dotted import path, the bare import path, and the public identifiers themselves
(`OptimizationParameters`, `Option(`, `Search(`) across every tracked `.py` in scope, and got
nothing but the definition lines. The limit: I did not search for reflective access
(`importlib`, `getattr` on a module object). If some upstream loader reaches modules by string
name, both could revive, and I did not audit for that mechanism. Both are inside the python
engine, not inside the locked game package, so neither is a LOCKED finding.

**`uploads/.env` is the row I would most want a second seat on.** The file is empty at HEAD, so
there is no leak and no STREAM consequence, which is why I tiered it MEDIUM rather than higher.
The defect is structural: `.gitignore:24` says `*.env`, someone nevertheless committed
`uploads/.env`, and git does not re-apply ignore rules to tracked paths. `aws_constants.py:7`
reads that exact path, so the file is the intended place to put live credentials. The
combination is a credential-leak footgun sitting in a submission repo. Whether it matters
depends on whether anyone still uses `aws_upload.py`, and C05-25 says nothing references it.

**The `utils/` misclassification is the largest single correction I am proposing, so here is
the basis rather than an assertion.** The path rule swept all 23 `utils/` files into `engine`.
Five of them are genuinely engine (the `game_analytics` chain plus
`analysis/distribution_functions.py`, all reached from `run.py`). Twelve are developer tooling:
`git ls-files 'utils/*.py' | xargs grep -ln "__main__"` returns exactly nine files, each an
executable CLI that operates on files the engine has already written, and three more
(`merge_luts/helper_funcs.py`, `merge_luts/lookup_properties.py`, `search_tool/forcetool_ids.py`)
are library modules whose only importers are those CLIs. I am not inferring the class from
their names: `games/README.md:13-14` calls them "six upstream developer utilities under
`utils/`", and `docs/records/V7_RECONCILIATION.md:29` says of the same set "These are developer
tools in the repository, not in the game and not in the maths upload." The project has already
made this classification in prose; the path rule simply could not see it. The remaining six
files under `utils/` are `__init__.py` stubs and `notes.md`.

**C05-40 is the row I would rank first for action, and it is a small one.** The staleness class
here is "utility default names a sample game that TR-088 deleted". The project ran a wider
sweep, found six, fixed five and deliberately left one unset, and wrote that up as complete in
two places. There are at least eight. `format_books_json.py:339` is the one that matters
because `Makefile:35` invokes it inside `make run`, so it is the only member of the class a
developer reaches without choosing to, and its printed usage line hands them
`games/0_0_tower_defense`. `swap_lookups.py:55` is the eighth. I did not extend the sweep beyond
`utils/`, so the class may be wider still, and the honest statement is that its size is UNKNOWN
rather than eight. That is the same failure the ledger records under Q-26: an enumeration that
searched a narrower file set than the class occupies.

**The generated artefact, because task 3 asked for exactly this shape.** `optimization_program/src/setup.toml`
is written, not authored: `run_script.py:39` opens `SETUP_PATH` in `"w"` and `toml.dump`s a dict
built at lines 30 to 34. I read the generator before judging the output, and the output fails.
