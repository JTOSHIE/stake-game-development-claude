### S2-C218, INCOMPLETE

The claim is true and the platform text is quoted correctly: `docs/stake-engine-live/2026-07-29/rgs.md:265-277` defaults an unknown code to `symbolAfter: true` and returns `` `${formattedAmount} ${meta.symbol}` ``, while `currency.ts:221-224` returns `` `${code} ${amount.toFixed(decimals)}` ``. The CI wiring is real (`checks.yml:393-395`) and the test really does only prove non-throwing (`currency.test.ts:87-88`, "ok('unknown code does not throw', ...)"), so a code-after-amount fallback is unasserted.

Where the finding is wrong is the parenthesis certifying `:185-194`, the main clause, as satisfied - and that error points at the more reachable instance. I measured the main clause at HEAD rather than reasoning about it: `Intl.NumberFormat('en', {style:'currency', currency:'ZZZ', currencyDisplay:'narrowSymbol'})` does not throw, and formats 500 as `"ZZZ 500.00"`. So for any well-formed but unmapped three-letter code the MAIN clause emits code-before-amount too, and the catch block is only entered for a MALFORMED code (`'US'` and `''` both throw RangeError; a real RGS sends neither). The finding therefore names the unreachable instance and clears the reachable one. The class is "an unmapped currency code renders code-first", and it lives in the Intl call, not the fallback.

Severity: LOW is right for the class and generous for the cited line. The reachable trigger is the platform adding a social or fiat code we do not hold in `VIRTUAL_CURRENCIES` and sending no `display` metadata, in which case a player sees "XPC 500.00" where the platform's own helper shows "500.00 XPC". The register row already discounts the obligation: `REGISTER.md:190` "Normative force is weaker than the other rows here: the page offers the functions as help rather than mandating them".
