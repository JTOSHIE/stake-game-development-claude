**S2-C060 (end-round fires before the presentation). CONFIRMED, and worse than claimed.**
Every citation is exact to the line, including `App.svelte:1414` and `:1445`. The platform text
at `rgs.md:37` describes the basic flow as one that "will close the round after all animations
have been complete", and `:39` says the reason plainly: for a longer round "you may want to save
where the user is up to watching incase they disconnect. When they reload the game in the
future, you can use the value found in round.event in the /wallet/authenticate API response".
Our `spin()` awaits `endRound` before it returns, so the round is closed before `animateSpin`,
before the free-spins presentation, and before the win count-up. I looked for a compensating
design and found one partial mitigation and one aggravation. **Mitigation:** `rgsService.ts`
does not publish the post-credit balance to the `balance` store (its only `balance.set` is at
`:733`, in authenticate); the new balance rides on `result.newBalance` and reaches the HUD via
`recordSpinResult` at `App.svelte:1495`, after the animation, so a player does not see the
balance jump early. **Aggravation:** `frontend/src/lib/stores/sessionRecovery.ts:207` gates the
whole recovery path on `if (!round || round.active !== true)`, and `App.svelte:575` derives
`liveBetID = get(activeRound)?.betID ?? null` for the checkpoint resume. Because end-round has
already fired, a re-authenticate can essentially never report an active round, so the ResumeOffer
("CONTINUE YOUR ROUND", `translations.ts:212`, `ResumeOffer.svelte:54`) and the recovered-round
presentation are unreachable in live play. A player who reloads mid free-spins therefore returns
to a balance that silently already contains the win, with no banner and no resume, which is
exactly the failure `sessionRecovery.ts` was written to prevent. That the owner checklist item 4
hedges "**If that prompt does not appear, that is the useful result and not a failure**"
(`OWNER_CHECKLIST.md:93`) reads as this defect already having been half-observed. HIGH is
correct and I would not argue it down. The file is LOCKED, so this needs an owner sanction; the
fix is an ordering change (return from `spin()` unsettled, settle after the presentation
resolves) and it touches the money path, so protocol rule 4's serial carve-out applies.

**S2-C061 (no clamp to the authenticated minBet and maxBet).** Verified and not refutable.
The platform conditions are verbatim at `rgs.md:287-288` and they are unconditional even though
bet levels themselves are not ("Although bet levels are not mandatory, bets must satisfy these
conditions"). `rgsService.ts:565-567` parses `minBet`, `maxBet` and `stepBet` into the auth
object, `:735` publishes only `rgsBetLevels`, and no production file reads any of the three: the
grep returns only `rgsService.contract.test.ts` (parse assertions at `:97-99`), the two store
tests' fixtures, `translations.ts` labels, and a `BetSelector.svelte:26` comment which
explicitly says `stepBet` "is NOT possible today and is not faked". So the three limits are
parsed and dropped, and the only bet model is the ladder. HIGH is right and the reachable path
is specific: when the authenticate response supplies no `betLevels` (which the platform says is
lawful), `activeBetLevels` falls back to the hardcoded `BET_LEVELS`, and every wager the game
can then submit is unchecked against the authenticated limits, so a spin can be rejected by the
wallet with the player watching. The claim's proof sweep is also correct: nothing asserts a
clamp, and the contract test asserting `minBet` is parsed is not the same assertion.
