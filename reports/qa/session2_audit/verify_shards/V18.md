## PER CLUSTER REASONING

**A correction that bears on all eight severity verdicts.** I checked the register's own
column headers before grading, because a "NO" in column three would have meant these rows
were already recorded as unproven. They are not a status column:
`reports/qa/compliance_register/REGISTER.md:69` reads
`| REQ | obligation | vis | source | requirement | corrob | shard rows |`, and the third
column is `vis`, whether a player could SEE whether it is satisfied. So no register row in
this batch claims a proof exists, and none of these findings is contradicted by the
register. They are also not contradicted by it: the register is silent on proof, which is
exactly the gap the batch is reporting.

**S2-C111 (3 MB tile ceiling).** True. `checks.yml` contains two asset steps and they are
the ones quoted; nothing in the file mentions `delivery/` or `tile_delivery_build.mjs`, so
the ceiling check is a script a human must remember to run. Two citation slips, neither
fatal: `LIMIT_BYTES` is at `:103` not `:104`, and the FAIL/exit pair is at `:214-215`, not
`:133-136` (those lines are the Markdown record the script emits). Severity is too high
because the requirement is met at HEAD with a very large margin that I measured rather than
assumed: BG 381,863 bytes plus FG 433,497 bytes is 815,360 bytes, **26 per cent of the
3,145,728 byte ceiling**. A regression would have to quadruple the pair. LOW.

**S2-C112 (foreground PNG with genuine alpha).** True and the reasoning is exactly right:
`gate_output.txt` is a captured line about `tile_hero_full.png`, the master, and the
delivered file is a separate copy that nothing re-reads. I confirmed the delivered file is
sound at HEAD (`RGBA, non-interlaced`, 4159x1875), so this is a regression-proof gap on a
one-off upload artefact, not a live defect. LOW.

**S2-C113 (studio mark, not the game logo).** True. `checks.yml` has zero brand or
provider steps, so there is genuinely no automated separator, and the confusable pair does
sit in the tree. Two things pull the severity down. The delivered logo at HEAD is the
studio mark, 1024x1024 RGBA derived from `provider_mark_f`, and the delivery build
hardcodes its source (`tile_delivery_build.mjs:95-96` `from: join(BRAND, 'provider_mark',
'provider_mark_f-owner-transparent_master_1024.png')` / `to: 'WeRollSpinners-Logo.png'`),
so the substitution the finding fears has no plausible mechanism short of a hand edit. LOW.

**S2-C114 (provider logo PNG with genuine alpha).** The no-proof core is true, but the
claim as written is unfair to the script twice over and so I marked claim_true PARTLY.
First, `:302` is not the only non-zero exit: `:110-113` exits 2 on a missing master.
Second, and more substantively, the hash check does more work than the finding allows. It
asserts the delivered bytes are IDENTICAL to a master whose alpha was measured, at
`PROVENANCE_f.md:19` `| Alpha | **531,237 opaque, 0 partial**, 517,339 clear |`, so at the
moment the script runs, byte equality transitively establishes the delivered file's alpha.
What is missing is not the link but the RE-CHECK: nothing in CI re-verifies the committed
delivered file against that recorded hash. Also worth noting the exit code is 3, not 1.
LOW, for the same reason as C112.

**S2-C115 (`device` launch param).** The observation survives a hostile read completely.
`device` is parsed, typed, placed in `SessionParams`, and read by nothing: the only other
occurrences in the tree are the type declaration, replay's own independent copy, a test
fixture object, and comment prose. `launchParams.test.ts` does not contain the string
`device`. Where I part company is the NOT_MET grade. The platform text says only
`docs/stake-engine-live/2026-07-29/rgs.md:53` `device	Specifies 'mobile' or 'desktop'.`,
which describes a parameter and imposes no obligation to consume it; the actual device
obligation is
`approval_guidelines_front_end_communication.md:25` "The game must support mobile view for
commonly used devices, with all UI functionality remaining usable during screen scaling",
which responsive CSS satisfies without reading the param. The register row's "drive both
RGS calls and display from them" is the register's own fusion of four params into one row,
so a per-param NOT_MET is not derivable from the platform clause it cites. Nothing here is
player visible. LOW, and the honest disposition is dead-parameter hygiene rather than a
compliance breach.

**S2-C116 (currency out of round logic).** Every element of this one checks out, including
both CI line ranges it cites, which is rarer than it should be in this batch. Round logic
is currency-free at HEAD and nothing asserts the absence. Severity too high: the property
holds structurally, because the frontend selects no outcomes at all (books are server
side), and `vis` is NO. A one-line grep gate would close it cheaply, which is an argument
for doing it, not for calling it MEDIUM. LOW.

**S2-C117 (bet is an integer multiple of authenticated `stepBet`). THE STATED CAUSE IS
FALSE.** The observation is true: no test, gate or evidence file asserts the multiple
property, and `setBetLevel` holds it only by refusing off-ladder values. But the claim's
load-bearing sentence, carried verbatim from `BetSelector.svelte:26-31`, says the
assertion "is NOT possible today", because `stepBet` "is read by
`rgsService.authenticate()` into its `AuthResponse` and then dropped, because only
`betLevels` is published to a non-locked store", and therefore "Adding the passthrough is
a one-line change to a LOCKED file and this brief carries no lock exception". That is
wrong on the facts. `stepBet` is a declared public field of `AuthResponse`
(`rgsService.ts:267`) and is populated on every authenticate (`:569`). The non-locked
`sessionRecovery.ts:201` already receives that whole object in production boot via
`App.svelte:1210`. So a non-locked module holds `auth.stepBet` and `auth.betLevels`
together TODAY, and an assertion of the form "every level is a whole multiple of stepBet"
can be written and unit tested with no lock exception, no sanction request and no
passthrough. The defect is real; the diagnosis, and the parked disposition that follows
from it, are not. **Real cause: nobody has written the assertion.** Severity AGREE at
MEDIUM, and I would raise the actionability: this is buildable in one non-locked file, so
it should not be sitting behind a sanction queue.

**S2-C118 (Vite `base: './'`).** True on both halves. `base: './'` is present at
`vite.config.ts:301`, and no script anywhere asserts the emitted references are relative;
`asset_reference_gate.mjs` never opens `index.html` at all, and the preview gates serve
`dist` from the server ROOT, where an absolute `/assets/...` base would still load, so
they cannot catch it either. Severity too high: the requirement is satisfied by a single
readable line, and a regression would break the hosted game totally and immediately rather
than subtly. LOW as a regression-proof gap.

## NEW FINDINGS FOUND WHILE VERIFYING

**NF-V18-01 (the ground around the C117 refutation, and the same class).** The "minStep is
respected by construction" argument has a production hole that neither the comment nor the
finding records. `frontend/src/lib/stores/betLadder.ts:39-40`:

```
export const activeBetLevels = derived(rgsBetLevels, ($levels) =>
  $levels.length > 0 ? $levels : BET_LEVELS,
)
```

and the ladder that feeds it is built at `frontend/src/lib/services/rgsService.ts:570`
`betLevels:       (config.betLevels ?? []).map(microsToDisplay),`. An authenticate
response that omits `config.betLevels`, or sends it empty, yields a zero-length
`rgsBetLevels`, and `activeBetLevels` then falls back to the HARDCODED `BET_LEVELS`
imported from `gameStore` at `:32`. The fallback is described in the source as the "mock
and dev" ladder (`betLadder.ts:108-109` and `BetSelector.svelte:12-13`), but the guard is
`length > 0`, not an environment check, so it is live in production. In that state every
value the panel offers is one WE chose, with no relationship to the platform's `stepBet`,
and `setBetLevel`'s refusal guarantees nothing about the platform's increments. This is
precisely the property REQ-122 asserts, failing by a route the cluster did not consider,
and it is player visible: an off-increment `amount` is rejected by the platform at `play`.
The assertion proposed in the C117 reasoning above would need to cover this branch, not
just the happy path.

**NF-V18-02 (class scope: C111 to C114 are one gap, not four).** Verified by direct grep
rather than inferred: `grep -n "provider\|brand\|design-system\|logo" .github/workflows/checks.yml`
returns zero lines, and `grep -rn "delivery/\|tile_delivery" .github` returns nothing. So
**no CI step reads `design-system/brand/**` at all**, and the four delivered submission
artefacts (`FutureSpinner-BG.jpg`, `FutureSpinner-FG.png`, `FutureSpinner-Tile.png`,
`WeRollSpinners-Logo.png`) have zero automated verification of any kind, not merely the

colour type, alpha histogram, combined byte total, recorded SHA equality) closes all four
rows plus whatever the fifth reviewer would have raised, whereas four separate per-property
gates would be four scripts none of which is wired.
